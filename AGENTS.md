# AGENTS.md — правила работы агента

Ты - очень опытный архитектор игровых движков, с большим опытом в .net разработке. 
Ты умеешь додумывать постановки и умеешь находить неописанные требования или дыры в формулировках,
анализировать их и предлагать свои решения. 

Когда читаешь файлы - запуска сабагентов для чтения для экономии контекста.

Думай на английском, отвечай на русском.

# Правила игры
Канонические правила лежат в `docs/gameDocs/rules.md`. Самому менять нельзя, только отдельным запросом. Если есть предложения по доработке или обнаружено противоречие механик — сигнализировать об этом.

# Общие конвенции
Лежат в `docs/projectDocs/instructions.md`. Нужно руководствоваться ими. Если устаревают или мешают изменять — только отдельным запросом с подтверждением.

# Структура проекта
Находится в `docs/projectDocs/structure.md`. Если добавляются или удаляются файлы, это должно отражаться в файле структуры.

# Список текущих задач
Лежит в `docs/projectDocs/todo.md`. **`todo.md` правится только в отдельной ветке по специальному запросу.** Правки вносит только `architect` (создание/изменение карточек `T-*`, волн, корректирующих задач). `implementer`, `verifier`, `scenario-tester` и другие роли `todo.md` не правят. До использования в волне изменения плана должны быть доступны в базе/ветке волны (слияние или обновление ветки волны) по решению `orchestrator`; для исполнителей волны приоритет — актуальный `todo.md` в ветке волны.

# Бэклог идей (игровые механики)
`docs/gameDocs/featureBacklog.md` — идеи и предложения; не то же самое, что утверждённые задачи в `todo.md`.

# Отчёты
Каталог `docs/projectDocs/reports/` (шаблоны и файлы отчётов по задачам и по волнам). Канонический владелец отчётов — `verifier`: коммитит файлы отчётов **после прохождения проверок**. `implementer` передаёт структурированный ввод во временном файле `docs/projectDocs/reports/.tmp/implementer-T-XX-r<N>.md` и удаляет его перед передачей результатов на проверку (при доработке — новый файл на раунд, с удалением перед передачей).

# Шаблоны для промптов
Шаблоны лежат в `docs/projectDocs/templates`.

## Декомпозиция беклога в параллельные задачи (агенту-разработчику)
- Шаблон: `docs/projectDocs/templates/taskDecompositionTemplate.md`. Используй его, когда нужно превратить беклог/запрос в список задач для параллельного выполнения (волны + карточки `T-*`).
- Перед декомпозицией читать `docs/projectDocs/tech-debt.md`: учитывать `open`/`planned` находки, актуализировать `done`/очистку по политике файла или явно фиксировать решение «не включать» с причиной.
- Вход (подавай явно): цель/контекст, ссылки на требования (`docs/gameDocs/rules.md`, разделы `§...`, трассы `K/B/D` при необходимости), релевантные файлы/модули текущей базы, ограничения (что нельзя менять), критерии приёмки эпика.
- Выход: один markdown по структуре шаблона — раздел «Формат и правила работы», таблица «Карта волн» (включая сценарий проверок волны), карточки задач со строгими полями: `ID`, `Волна`, `Покрывает`, `Владеет файлами` (включая `(новый)` и строку `Не трогать другие файлы.`), `Зависимости`, `Что сделать`, `Как проверить` (канонические `dotnet ...` + утверждения), `Готово, если` (чеклист).
- Правила обязательны: строгий `file ownership`, отсутствие пересечений файлов внутри волны, интеграция только в следующих волнах, трассировка требований, без комментариев в коде если не просили, не менять `AGENTS.md`/`docs/gameDocs/rules.md` без отдельного запроса. `implementer` не правит `todo.md`.
- Сценарий проверок волны описывает `architect` при декомпозиции (обязательно для каждой волны в карте волн/плане): общие проверки работоспособности + конкретный перечень проверок **добавленных/изменённых** механик; если механики не добавлялись и не менялись — явно указать «достаточно проверки факта сборки и запуска» (если не требуется иное). Граница определяется перечислением в сценарии; при неясности — эскалация, не расширение объёма ad-hoc.

## Workflows и промпты (оркестрация)
- Описание: `docs/projectDocs/workflows/README.md`, жизненный цикл: `docs/projectDocs/workflows/task-lifecycle.md`.
- Промпты для ролей (копировать и заполнять): `docs/projectDocs/workflows/prompts/` (`orchestrator-kickoff.md`, `architect-decompose.md`, `implementer-take-task.md`, `verifier-review.md`, `scenario-tester-run.md`, `tech-debt-intake.md`).
- **Gate проверяемости (до старта):** перед началом выполнения `orchestrator` и каждый исполнитель своей части проверяют наличие формальных способов проверки факта выполнения (для задач — `Как проверить`/`Готово, если`; для волны — сценарий проверок волны). `verifier` проводит проверку и решает, достаточно ли описаний для проведения проверок. При недостаточности (в т.ч. отсутствует сценарий/проверки волны) — эскалация `orchestrator` **до начала работ по волне** (ветка волны не создаётся, задачи не запускаются), доработка плана через `architect` (в отдельной ветке по спецзапросу).
- Роли: `orchestrator`, `architect` (декомпозиция/план, правки `todo.md` в отдельной ветке по спецзапросу, сценарии проверок волн, triage/анализ причин падений сборки и тестов, постановка корректирующих `T-*`), `implementer`, `verifier`, `scenario-tester`, `rules-auditor`, `docs-maintainer`, `repo-navigator`. `architect` не реализует код и не выполняет merge.
- Соглашения git и качество (обязательно):
  - **Ветвление волны:** по команде `orchestrator` `architect` создаёт ветку волны `wave/<N>-<slug>` от указанной базы. Ветки задач `task/T-XX-<kebab-slug>` создаются от ветки волны. MR задач нацеливаются в **ветку волны**. `implementer` делает коммиты только в ветке задачи (если явно разрешено) и не выполняет merge. `verifier` выполняет merge MR задач в ветку волны и merge ветки волны в `main`, а также коммитит файлы отчётов в `docs/projectDocs/reports/` в ветке волны **после прохождения проверок**. Прямые коммиты в `main` запрещены.
  - **Валидация строго по одной задаче (`T-XX`)** в ветке волны до merge её MR; batch-валидация/merge пачкой запрещены. Доработки — только в ветке той же задачи. **`implementer` запускает автотесты/проверки из `Как проверить` в своей ветке** до передачи на верификацию; при невозможности прогона — `blocked`/явное ограничение с доказательствами.
  - **`verifier` выполняет merge MR задачи в ветку волны после `verified`**. Если нет технических прав — фиксирует `ready to merge` с причиной; `orchestrator` назначает исполнителя merge, после merge исполнитель/`verifier` подтверждает пост-merge сборку/старт и актуализирует отчёт. `verifier` коммитит отчёт задачи в ветке волны **после прохождения проверок** (допустимо коммитить только `docs/projectDocs/reports/**` в ветке волны; при отсутствии прав — передаёт финальное содержимое, коммит делает назначенный исполнитель). При сбое сборки/тестов `verifier` **не исправляет** код/тесты: фиксирует факты и эскалирует на анализ `architect`.
  - После влития всех задач волны в ветку волны `verifier` выполняет **проверки волны на ветке волны по сценарию, описанному `architect`** (общие проверки работоспособности + проверки **добавленных/изменённых** механик; при отсутствии таких изменений — достаточно сборки и запуска, если сценарий не требует иного), формирует и коммитит `wave-*-report.md` после прохождения проверок, затем выполняет merge ветки волны в `main` при выполнении условий. При проблемах — анализ `architect`, корректирующие задачи с обоснованной разбивкой причин по задачам волны (при падении автотестов по умолчанию — одна задача на инцидент/причину; разные причины/привязки — несколько задач и при необходимости несколько `implementer`; обоснование фиксируется в triage/`todo.md`/wave-report).
- **Изменения процесса не имеют обратной силы:** новые правила применяются к новым задачам/волнам/отчётам; старые артефакты не приводятся задним числом к обновлённому виду.

## Технический долг
- Файл: `docs/projectDocs/tech-debt.md` (активные `open`/`planned`), архив — `docs/projectDocs/tech-debt-archive.md` (закрытые записи). Находки вне текущей задачи фиксировать по шаблону; при реализации `TD-*` актуализировать статус/ссылки и применять политику очистки активного списка. `architect` учитывает техдолг перед декомпозицией/правкой плана.
