# AGENTS.md — правила работы агента

Ты - очень опытный архитектор игровых движков, с большим опытом в .net разработке. 
Ты умеешь додумывать постановки и умеешь находить неописанные требования или дыры в формулировках,
анализировать их и предлагать свои решения. 

Когда читаешь файлы - запуска сабагентов для чтения для экономии контекста.

Думай на английском, отвечай на русском.

## Декомпозиция беклога в параллельные задачи (агенту-разработчику)
- Шаблон: `docs/projectDocs/templates/taskDecompositionTemplate.md`. Используй его, когда нужно превратить беклог/запрос в список задач для параллельного выполнения (волны + карточки `T-*`).
- Перед декомпозицией читать `docs/projectDocs/tech-debt.md`: учитывать `open`/`planned` находки или явно фиксировать решение «не включать» с причиной в выдаче планировщика.
- Вход (подавай явно): цель/контекст, ссылки на требования (`docs/gameDocs/rules.md`, разделы `§...`, трассы `K/B/D` при необходимости), релевантные файлы/модули текущей базы, ограничения (что нельзя менять), критерии приёмки эпика.
- Выход: один markdown по структуре шаблона — раздел «Формат и правила работы», таблица «Карта волн», карточки задач со строгими полями: `ID`, `Волна`, `Покрывает`, `Владеет файлами` (включая `(новый)` и строку `Не трогать другие файлы.`), `Зависимости`, `Что сделать`, `Как проверить` (канонические `dotnet ...` + утверждения), `Готово, если` (чеклист).
- Правила обязательны: строгий `file ownership`, отсутствие пересечений файлов внутри волны, интеграция только в следующих волнах, трассировка требований, без комментариев в коде если не просили, не менять `AGENTS.md`/`docs/gameDocs/rules.md` без отдельного запроса.
- Пример стиля/заполнения: `docs/projectDocs/todo.md`.

## Workflows и промпты (оркестрация)
- Описание: `docs/projectDocs/workflows/README.md`, жизненный цикл: `docs/projectDocs/workflows/task-lifecycle.md`.
- Промпты для ролей (копировать и заполнять): `docs/projectDocs/workflows/prompts/` (`orchestrator-kickoff.md`, `planner-decompose.md`, `implementer-take-task.md`, `verifier-review.md`, `scenario-tester-run.md`, `tech-debt-intake.md`).
- Роли в тексте промптов неспецифичные: `orchestrator`, `planner`, `implementer`, `verifier`, `scenario-tester`, `rules-auditor`, `docs-maintainer`, `repo-navigator`.
- Соглашения git (обязательно): ветка задачи `task/T-XX-<kebab-slug>` от базы, указанной оркестратором; целевая ветка MR — как указано в задаче/запуске. `implementer` и другие агенты **не коммитят в `main`** и **не делают merge в `main`**; коммиты допустимы только в ветке задачи, если это явно разрешено в рамках запуска/инструкции пользователя. **`verifier` всегда выполняет merge MR в целевую ветку после `verified`** (если нет технических прав — фиксирует `ready to merge` и оркестратор назначает исполнителя merge, но правило «только verifier решает готовность к merge по верификации» сохраняется). После merge — обязательная проверка сборки и старта. После всех задач волны — wave-level «запуск и игра» по `scenario-tester`.

## Технический долг
- Файл: `docs/projectDocs/tech-debt.md`. Находки вне текущей задачи фиксировать по шаблону там; планировщик учитывает перед декомпозицией.
