# FS-007 — Составные подразделения

- **Статус:** ready_for_decomposition
- **Источник:** `docs/gameDocs/featureBacklog.md` #7 «Составные подразделения (в пехотном полку сколько-то пехотных батальонов, придана своя полевая артиллерия, есть разведчики)»; запрос оркестратора (режим A, 2026-11-20).
- **Связанные правила:** `docs/gameDocs/rules.md §1` (начальник штаба корпуса, истину показывает только разбор), `§2` (юниты — полки, батальоны, артиллерия, разведка, штаб; параметры юнита; открытая стартовая информация; совместные эффекты f(командир)×f(состав)), `§3` (один приказ — одному юниту, пул курьеров), `§4` (закрытые слоты/намерения, `support` — район или юнит, шаблоны приказов), `§5` (четыре стадии приказа, донесение с четырьмя полями), `§6` (туман войны, разведка с уверенностью 3, `fact key`), `§7` (сила стороны, `CombatEffective`, расход боезапаса), `§9` (`guard`/`escort`, совмещение задач), `§11` (цели по конкретному юниту, AAR), `§12` (параметры/валидация профиля, детерминизм, replay, сохранение), `§14` (пример тайминга).
- **Владелец спеки:** analyst

## Цель и ценность
- Дать сценарию возможность описать порядок боя составного подразделения: пехотный полк как штаб/ядро плюс несколько пехотных батальонов, приданная полевая артиллерия и разведчики — не вводя новых игровых правил и не ломая существующий конвейер «приказ → понимание → исполнение → донесение».
- Повысить читаемость брифинга, карты/обстановки и разбора: игрок видит структуру своего полка и связи элементов, а истину о структуре противника узнаёт только из донесений/разбора.
- Сохранить детерминизм, replay, save/load и симметрию сторон: состав — статические данные сценария, а не новая случайность или скрытый источник силы.

## Бизнес-поведение и сценарии

### 1. Сущности и модель (что добавляется)
- Вводится **формация** (`Formation`) — описательный уровень организации боя: `id`, `name`, `faction`, список участников `unitId + role`, ровно один уровень вложенности (полк → батальоны/артиллерия/разведка). Формация **не является юнитом**, не имеет силы, боеготовности, морали, боезапаса, характеристик командира, приказов и не является адресатом приказа.
- Все участники формации — обычные `Unit` по `§2` с собственными характеристиками, приказами и донесениями. Роли участников — метки порядка боя, отображаемые в брифинге/UI:
  - `RegimentHeadquarters` — штаб/ядро полка (`UnitType.HQ` либо `Infantry` для совместимости с существующими сценариями);
  - `InfantryBattalion` — пехотный батальон (`UnitType.Infantry`);
  - `AttachedArtillery` — приданная полевая артиллерия (`UnitType.Artillery`);
  - `AttachedRecon` — разведчики (`UnitType.Recon`).
- «Приданность» артиллерии и разведчиков — **статическая организационная связь в данных сценария**. Она не создаёт автоматических приказов, автоматической поддержки, дополнительных линий связи или изменений в формулах боя.

### 2. Инициализация сценария
- Сценарий по желанию объявляет формации; при отсутствии объявления сценарий остаётся плоским и валидным (опт-ин).
- Загрузчик создаёт все единицы как обычно; формация только ссылается на уже существующие `unitId`. Валидация: уникальность `id` формаций и участников, существование каждого `unitId`, одинаковая `Faction` у формации и всех участников, отсутствие повторного включения юнита в две формации, отсутствие вложенных формаций, соответствие роли типу юнита, непустой список участников.
- `InitialStrengthSnapshot` каждого юнита остаётся его собственным снимком (`§7`, `§11`); сила штаба/ядра **не** складывается из сил батальонов. Если сценарий сохраняет цель `PreserveStrength` на старый `id` полка, этот `id` остаётся у штабного юнита; добавленные батальоны — новые юниты с новыми `id` (баланс сценария — ответственность автора).

### 3. Игра (поведение в отрезках)
- **Приказы.** Штаб по-прежнему отдаёт приказ одному юниту через курьера (`§3`), приказ проходит четыре стадии (`§5`). Приказа «всем батальонам полка» нет: чтобы сдвинуть состав, игрок отдаёт отдельные приказы каждому участнику, оплачивая курьеров по общим правилам. Внутренней передачи приказа от штаба полка батальонам в MVP нет.
- **Поддержка артиллерии.** Приданная артиллерия — обычный юнит. Поддержка полка/батальона выражается обычным намерением `support` с целью «район или юнит» (`§4`) и обычным курьером; постоянного автоматического режима support из факта придания нет. Боевой расчёт артиллерии — общий для всех типов юнитов (`§7`); дальность прицельного огня и специфическое снаряжение — backlog #8, в эту спеку не входят.
- **Разведчики.** Приданный разведюнит подчиняется `§6`: успешное наблюдение даёт точный доклад с уверенностью 3, провал — правилам двухшаговой разведки. Членство в формации не добавляет бонусов к наблюдаемости/обнаружению и не меняет `fact key`.
- **Бой.** `§7` не меняется: в зоне сила стороны суммируется по всем боеспособным юнитам стороны, потери распределяются по существующим правилам. Формация не добавляет ни силы, ни множителей, не создаёт второй агрегат «полк» рядом с батальонами (исключение двойного счёта).
- **Движение, охранение, конвои.** Участники действуют по общим правилам `§4`, `§9`; формация не даёт привилегий и не совмещает задачи за юнит.

### 4. Туман войны, знание и разбор
- Структура **своего** полка (имена/роли/типы/стартовую силу участников) доступна игроку с начала сценария как часть известного стартового состояния; это не раскрывает скрытых черт/боевого опыта сверх `§2`.
- Структура **вражеской** формации не попадает в `PlayerKnowledge` и не показывается в UI до донесения/наблюдения; истина видна только в разборе (`§1`, `§6`). Донесения сохраняют четыре обязательных поля и источник — конкретный `unitId`; нового `ReportKind` не требуется.
- AAR может показать полное дерево формации как истину; метрики и цели считаются по конкретным юнитам (`§11`), формация метрик не добавляет.

### 5. Детерминизм и сохранение
- Формации — статический контент без RNG; порядок итерации участников детерминирован (стабильный порядок в данных сценария). При смене seed истина не меняется (`§12`).
- Версионированный снимок сохранения включает формации (или однозначно восстанавливается из сценария) и проходит round-trip без потери связей; загрузка того же снимка и ввода воспроизводит ход дальше без расхождений.

### 6. Примеры сценариев
- **A (своя формация):** сценарием задана формация `12IR` — штаб `12IR`, батальоны `12IR-1BN`/`12IR-2BN`, `12IR-ART` (Artillery), `12IR-REC` (Recon). Брифинг показывает дерево; игрок отдаёт четыре приказа разным юнитам; в зоне B3 силы сторон суммируются по `§7`; успешный доклад `12IR-REC` имеет уверенность 3.
- **B (вражеская формация):** формация Red объявлена в контенте, но игроку невидима; знание появляется только из донесений, в разборе — полностью.
- **C (валидация):** загрузка отклоняет неизвестного участника, смешанную faction, двойное включение юнита, вложенную формацию и несоответствие роли типу юнита.
- **D (persistence/replay):** save → load сохраняет состав; повторный прогон с тем же seed даёт те же донесения и истину.

## Scope / Non-scope
- **In scope:** формация как статические данные порядка боя; роли `RegimentHeadquarters`/`InfantryBattalion`/`AttachedArtillery`/`AttachedRecon` поверх существующих `UnitType`; валидация контента; отображение своей структуры в брифинге/обстановке и сокрытие вражеской до донесения/разбора; совместимость с приказами, боем, разведкой, целями и AAR без изменения их правил; симметрия для противника; детерминизм и save/load; opt-in для сценариев.
- **Out of scope:** приказы/цели уровня формации и внутренняя делегация приказов; автоматическая или постоянная огневая поддержка «по факту придания»; динамическое перепридание/переподчинение и переорганизация от потерь; несколько уровней вложенности (корпус → полк → батальон); агрегаты силы/морали/потерь формации и новые типы целей (цели — по юниту, `§11`); дальность/прицельность/спецснаряжение артиллерии (backlog #8); новые `UnitType`; новые события, RNG-роллы и новые типы донесений.

## Разрешённые неоднозначности и решения
| Вопрос | Решение | Основание/ссылка |
|---|---|---|
| Нужны ли новые типы юнитов для «батальон/артиллерия/разведка»? | Нет. Батальон, артиллерия, разведка и штаб уже являются юнитами; вводятся только роли-метки поверх существующих `UnitType`. | `rules.md §2`; `Kriegsspiel.Core/Domain/Unit.cs` (`UnitType.Infantry/Artillery/Recon/HQ`). |
| Является ли формация юнитом/боевым актором? | Нет. Формация — описательные данные сценария; акторы — обычные юниты. Сила/снимок штаба не равны сумме сил батальонов. | `§2` (параметры у каждого юнита), `§7`/`§11` (`InitialStrengthSnapshot` на юнит), исключение двойного счёта. |
| Кто командует батальонами и приданными средствами? | Штаб игрока отдельно; один приказ — одному юниту, отдельный курьер на каждый. Внутренней передачи приказа от полка в MVP нет. | `§3` «ПРИКАЗ — отдать приказ одному юниту», пул курьеров; `§5` (четыре стадии на юнит). |
| Что означает «придана полевая артиллерия»? | Статическая связь в порядке боя для брифинга/UI. Тактическая поддержка — обычный приказ `support` (район/юнит); автоматического огня/подчинения нет. | `§4` (намерение `support`, цель — район или юнит), `§7` (общая формула боя для всех юнитов). |
| Нужна ли особая уверенность для «своих» разведчиков? | Нет. Разведка участника использует общие правила; уверенность 3 — только при успешном наблюдении, бонуса от формации нет. | `§6` (двухшаговая разведка, confidence 3). |
| Меняется ли агрегация боя из-за формации? | Нет. Сила стороны уже считается по всем присутствующим юнитам стороны; формация не добавляет множителей и отдельной стороны. | `§7` (сила стороны), текущий `CombatResolver` (сумма по фракции). |
| Доступна ли структура противника игроку с начала? | Нет. Своя — да (стартовые данные); вражеская — только через донесения/наблюдение и полностью в разборе. | `§1`, `§6` (истину видит только разбор); `§2` перечисляет конкретную открытую стартовую информацию, а не вражеский порядок боя. |
| Влияет ли фича на RNG/replay? | Нет. Состав статичен, RNG не добавляется; порядок участников фиксирован данными сценария. | `§12` (детерминизм, seed, replay). |
| Какова глубина вложенности? | Один уровень: формация полка содержит юниты. Более глубокие структуры не поддерживаются. | `§1` (штаб корпуса оперирует несколькими подразделениями), в каноне нет многоуровневой иерархии. |
| Что делать с существующим сценарием `12IR`? | Формации опт-ин; существующие сценарии остаются плоскими. При конвертации `id` полка остаётся у штабного юнита, чтобы цели `PreserveStrength` не сломались; новые батальоны получают новые `id`. | `§11` (цели по конкретному юниту), требование обратной совместимости контента. |

**Эскалация при изменении требований (не открытый вопрос текущей спеки):** если заказчик потребует приказы уровня полка с внутренней делегацией, автоматическую постоянную поддержку приданной артиллерии, агрегатные цели/метрики формации или динамическое переподчинение — это потребует правки канона `rules.md` (как минимум `§3`, `§5`, `§7`, `§11`, `§12`) и заключения `rules-auditor` отдельным запросом. Настоящая спека таких изменений не предполагает и канон не меняет.

## Критерии готовности к декомпозиции / приёмки (бизнес)
- [ ] Сценарий может объявить формацию со штабом, одним и более батальонами, приданной артиллерией и разведкой на существующих `UnitType`; загрузчик принимает такой контент и отклоняет невалидный (неизвестный `unitId`, разные faction, дубль участника, вложенность, несоответствие роли типу, пустой состав).
- [ ] Ни один показатель юнита не суммируется автоматически в формацию/штаб; итог боя и `CombatEffective` соответствуют `§7`, двойной счёт силы исключён (регрессионные проверки боя).
- [ ] Конвейер приказов не изменён: один приказ на один юнит, курьеры/ETA/журнал по `§3`; приказов и API уровня формации нет.
- [ ] `support` как обычный приказ к району/юниту работает по `§4`; факт придания не порождает автоматических действий артиллерии.
- [ ] Разведчик формации использует `§6`; уверенность 3 выдаётся только при успешном наблюдении; новых бонусов и новых типов донесений нет.
- [ ] Своя структура видна в брифинге/обстановке; вражеская отсутствует в знании игрока до донесения/разбора; четыре поля донесения и источник сохранены.
- [ ] Save/load сохраняет формации; повтор с тем же seed воспроизводит ту же истину; новых RNG-роллов нет.
- [ ] AAR показывает структуру как истину; цели и метрики остаются по конкретным юнитам (`§11`); сценарии без формаций работают как прежде.

## Примечания для architect
- **Ориентир по подсистемам (не нарезка задач):** домен (тип `Formation`, enum ролей, связь в `GameState`/контенте), `Content`/загрузчик/валидация (`§12`), `Console` (брифинг и обстановка — только через знание игрока, без чтения вражеской истины), persistence/DTO (версия снимка), тесты валидации, «нет двойного счёта», fog-границ и round-trip. Изменения в `rules.md`/`AGENTS.md` не нужны.
- **Зависимости/совместимость:** не зависит от других `FS-*`; пересечение с FS-001 (выбывание командиров) только через identity юнита — конфликтов нет. Существующий план `todo.md` (Wave 0–3) не меняется этой спекой; декомпозиция — отдельный запрос.
- **Риски для декомпозиции:** конвертация плоских сценариев в формации может изменить баланс (новые юниты); сохранять `id` исходного полка за штабным юнитом. Не допускать утечки вражеской формации в UI/сохранении/AI-контекст.
- **Проверяемость:** критерии выше сформулированы как проверяемые утверждения; сценарий проверок волны должен включить валидацию контента, регрессию боя `§7`, границу знания «свой/вражеский», `support`/recon по `§4`/`§6` и save/replay.
