# FS-024 — «Выступает через x переходов»: семантика перехода и отображение оценки движения

- **Статус:** ready_for_decomposition
- **Источник:** `docs/gameDocs/featureBacklog.md` #27 «Что значит выступает через x переходов?»
- **Связанные правила:** `docs/gameDocs/rules.md §2` (карта — граф районов: соседи и время перехода до них в минутах, рёбра трёх типов, дельты боеготовности «за ребро», время перехода по рёбрам как параметр сценария), `§3` (30-минутные отрезки, «выступление» в порядке событий, минуты как единица времени, часы идут только по `ВРЕМЯ +30`, журнал с расчётным/фактическим временем), `§4` (слот «Куда», режим передвижения, срок прибытия), `§5` (стадия 3 — исполнение/движение по маршруту через промежуточные зоны; стадия 4 — донесение с четырьмя полями), `§6` (знание ≠ истина, донесения с задержкой, уверенность обычного источника ≤2, метки времени события/доставки), `§12` (параметры мира/переходов, детерминизм/replay, версионированное сохранение), `§14` (пример тайминга доставки и выступления). Спека не изменяет канон правил.
- **Владелец спеки:** analyst

## Цель и ценность
- Ответить на вопрос игрока из backlog #27 однозначно: что именно означает число в сообщении «выступает через x переходов» и как по нему планировать время.
- Дать начальнику штаба пригодную для планирования оценку: сколько участков пути предстоит пройти и когда подразделение ориентировочно прибыло бы по текущему плану, без раскрытия скрытой истины и без изменения хода времени.
- Устранить существующую неполноту формулировки (только число рёбер без времени/прибытия и некорректная форма «1 переход(ов)») как задачу представления донесения, а не новую игровую механику.

## Бизнес-поведение и сценарии

### 1. Установленная семантика «перехода» (факты канона и кода)
- **«Переход» = один участок маршрута между соседними зонами, то есть обход одного ребра графа** (hop), а не ход `ВРЕМЯ +30`, не минута и не задержка приказа. Обоснование: `rules.md §2` задаёт у района «соседи и время перехода до них в минутах» и рёбра трёх типов; таблица дельт боеготовности считается «за ребро»; `§12` относит «время перехода по рёбрам» к параметрам мира; `§5` стадия 3 описывает выдвижение «по маршруту через промежуточные зоны».
- В коде фраза формируется в `Kriegsspiel.Core/Arbitration/ExecutionResolver.cs:88` как донесение `{unit.Name}: выступает в {target} через {plan.Steps.Count} переход(ов).` (`ReportKind.Status`). `plan` — `RoutePlan` из `Kriegsspiel.Core/Arbitration/PathPlanner.cs:7-23`: каждый `RouteStep` содержит `FromZoneId`, `ToZoneId`, `EdgeId`, `EdgeType`, `Minutes` и дельты состояния; маршрут строится кратчайшим **по суммарному времени** (`PathPlanner.cs:79-115`). Следовательно `Steps.Count` — число рёбер, а `TotalMinutes` — сумма минут по рёбрам. Тест `Kriegsspiel.Core.Tests/ExecutionResolverTests.cs:12-26` фиксирует: маршрут A→B→C имеет 2 шага и 50 минут (30+20).
- Сообщение — **оценка на момент выступления по текущему плану и текущей проходимости**, а не факт прибытия: время пересчитывается в зависимости от режима передвижения и местности (`PathPlanner.TravelMinutes`), маршрут может измениться при непроходимости ребра/сроке (`ExecutionResolver.Impossible`, `TryImprovise`), а контакт в промежуточной зоне прекращает движение (`ExecutionResolver.OnMove`, `ReportKind.Contact`). Само число минут не обязано быть кратным 30: 30 минут — шаг игрока (`§3`), а не длина ребра.

### 2. Ожидаемое отображение игроку
- Текст донесения должен давать три связанные величины: **N переходов + ориентировочное время в пути + ориентировочное время прибытия**. Пример: `12-й полк: выступает в B3 — 3 перехода, ~65 мин в пути, прибытие ориентировочно 08:05 (по плану).`
  - `N` — число шагов текущего плана (`RoutePlan.Steps.Count`); при N>1 это N−1 промежуточных зон и целевая зона.
  - Время в пути — `RoutePlan.TotalMinutes` (сумма минут по рёбрам выбранного маршрута с учётом режима передвижения).
  - Ориентировочное прибытие — минута выступления/`OrderAccepted` + время в пути; показывается как оценка («ориентировочно/по плану»), а не как факт. В журнале сохраняются обе минуты: события и доставки донесения (`§5-6`); расчётное/фактическое время доставки уже показывается журналом по `§3`.
- Формулировка «переход(ов)» заменяется на грамматически верную форму для числа (`1 переход`, `2 перехода`, `5 переходов`); семантика числа от этого не меняется.
- Значение остаётся **содержанием донесения своего подразделения** (`ExecutionResolver.StatusReport`, `§5` стадия 4, `§6`) с четырьмя обязательными полями (минута события, минута доставки, источник, уверенность; обычный источник ≤2). Пока донесение не доставлено, игрок не видит оценку; потеря/задержка донесения работает по общим правилам. Числовые N/время/ETA не должны превращаться в прямое знание истины симуляции.
- Названия промежуточных зон и типы рёбер в тексте оценки показываются только в объёме топологии, уже доступной игроку (`§6`, карта знания); минимально достаточная форма — только числа N/минуты/прибытие.

### 3. Случаи 0 / 1 / много / неизвестно
| Случай | Ожидаемое поведение и текст | Основание |
|---|---|---|
| **0 переходов** | Юнит уже в целевой зоне: отдельное донесение `уже в {target}` (`ReportKind.Arrival`), ни «через 0», ни время в пути, ни ETA не показываются. Для намерений без перемещения (`hold`/`reserve`/`guard`) показывается статус «в зоне, задача …» без маршрута. | `ExecutionResolver.cs:49-69`; `§4` (слот «Куда», намерения); `§5` стадия 4. |
| **1 переход** | Целевая зона — соседняя: `1 переход, ~M мин, прибытие ориентировочно …`; единственное число, без `(ов)`. | `PathPlanner.RouteStep`; `§2` (время перехода до соседа). |
| **Много переходов (N>1)** | `N переходов` — число рёбер кратчайшего по времени маршрута; в пути — сумма минут всех шагов; ETA — от минуты выступления. Множественное число согласуется с N. | `PathPlanner.TryPlan`; `§2`, `§3`, `§12`. |
| **Неизвестно / нет оценки** | Если нет доступной цели, маршрута, ребро непроходимо или сорван срок, вместо N/ETA приходит донесение о невозможности (`ReportKind.Impossible`) с причиной (`нет доступной цели`, `нет маршрута в …`, `ребро … непроходимо`, `срок прибытия истёк`, `опоздание к сроку`) — число переходов не выдумывается. Если донесение ещё не доставлено/потеряно, игрок видит отсутствие статуса, а не «неизвестно» с вымышленным ETA. | `ExecutionResolver.cs:56-83,113-149,222-265`; `§5-6` (доставка, неполные/устаревшие донесения). |
| **Оценка устарела в пути** | При обходе препятствия/смене маршрута действует новая оценка из нового донесения; старые N и ETA не подаются как актуальные. При контакте в промежуточной зоне приходит донесение о контакте, а не о прибытии; ETA считается сорванным. | `ExecutionResolver.Impossible/TryImprovise/OnMove`; `§5` стадия 3 (контакт до прибытия), `§6` (устаревшее донесение). |

### 4. Сценарии проверки (бизнес-уровень)
1. Игрок отдаёт приказ на соседнюю зону: видит «1 переход», минуты и ETA; число согласовано с конфигурацией ребра из сценария.
2. Приказ в зону через несколько рёбер: число переходов равно числу рёбер кратчайшего по времени пути, время — сумме минут, ETA — минута старта + сумма; режим передвижения меняет минуты и ETA, но не обязан менять N (если топология та же).
3. Цель — текущая зона: игрок видит «уже в зоне», а не «0 переходов».
4. Разрушенный мост/отрезанное ребро/отсутствие маршрута/истёкший срок: донесение о невозможности с причиной, N/ETA не показываются.
5. Контакт в промежуточной зоне или перепланирование маршрута: приходит соответствующее донесение; ранее показанная оценка явно перестаёт быть актуальной.
6. Повторный прогон с тем же seed и вводом даёт те же N/минуты/ETA и тот же порядок донесений; загрузка снимка воспроизводит оценку (`§12`).

## Разрешённые неоднозначности и решения
- **Вопрос:** Что такое «переход» — ребро, участок маршрута или время?
  - **Решение:** Один проход по ребру графа между соседними зонами (`RouteStep` / `EdgeId`), а не ход игры и не минута. Число «x» — количество таких участков в запланированном маршруте.
  - **Основание:** `rules.md §2` («соседи и время перехода до них в минутах», рёбра, «за ребро»), `§5` (маршрут через промежуточные зоны), `§12` (время перехода по рёбрам); `PathPlanner.RouteStep`, `ExecutionResolver.cs:88`. Противоречия канона нет — blocked не требуется.
- **Вопрос:** Откуда берутся число и время, если в правилах нет поля «переходы»?
  - **Решение:** Число = `RoutePlan.Steps.Count`; время в пути = `RoutePlan.TotalMinutes`; ETA = минута старта + это время. Величины детерминированно выводятся из уже существующего плана, новый RNG/состояние не вводятся.
  - **Основание:** `PathPlanner.TryPlan` (кратчайший путь по времени), `ExecutionResolver.cs:78,86-88,143`, тест `ExecutionResolverTests.cs:12-26`; `§3` (мир в минутах), `§14`.
- **Вопрос:** Не противоречит ли показ минут пошаговому времени `ВРЕМЯ +30` (`§3`)?
  - **Решение:** Нет. Минуты — длительность ребра/вся оценка в минутах внутри отрезка; часы по-прежнему двигаются только действием `ВРЕМЯ +30`. ETA — расчётное время в донесении/журнале, а не автоматическое продвижение игры.
  - **Основание:** `§3` («мир живёт в минутах; игрок видит только границы отрезков», журнал с расчётным временем), `§14`.
- **Вопрос:** Что показывать при 0/1/много/неизвестно?
  - **Решение:** По таблице раздела 3: 0 → «уже в зоне» вместо «через 0»; 1 → единственное число; N>1 → число рёбер; неизвестно/невозможно → `Impossible`-донесение с причиной без вымышленных N/ETA, а при отсутствии доставленного донесения — никакой оценки.
  - **Основание:** ветки `ExecutionResolver.Start`, `Impossible`, `OnMove`; `§3-6` (доставка донесений, знание vs истина).
- **Вопрос:** Является ли это исправлением дефекта или новой механикой?
  - **Решение:** Исправление/уточнение представления существующего донесения: механика маршрута и времени уже реализована и описана каноном; добавляются только осмысленная формулировка и недостающие числа из того же плана.
  - **Основание:** `ExecutionResolver.cs:88` (существующая строка без времени), `PathPlanner` (данные уже есть); `§2,§5,§12`.
- **Вопрос:** Требуется ли эскалация к `rules-auditor` или правка канона?
  - **Решение:** Нет. Все решения выводятся из действующих `§2,§3,§5,§6,§12` и текущей модели; отдельный запрос на изменение `rules.md` не нужен.
  - **Основание:** сопоставление формулировок и кода с указанными разделами; активных `TD-*` по теме в `docs/projectDocs/tech-debt.md` нет.

## Критерии готовности к декомпозиции / приёмки (бизнес)
- [ ] Зафиксировано и проверяемо: «переход» — ребро маршрута; N = число шагов плана, время = сумма минут шагов, ETA = минута выступления + время; N не равен числу ходов `ВРЕМЯ +30`.
- [ ] Донесение о выступлении содержит N, ориентировое время в пути и ориентировочное прибытие с пометкой «по плану/ориентировочно»; форма числа грамматически корректна для 1/2/5.
- [ ] Случай 0: «уже в зоне»/`Arrival`, без «через 0» и ETA; случай без перемещения — статус без маршрута.
- [ ] Случаи 1 и N>1 дают корректные N, минуты и ETA; N>1 соответствует числу рёбер кратчайшего по времени маршрута (N−1 промежуточных зон).
- [ ] При отсутствии цели/маршрута, непроходимом ребре, сорванном сроке, контакте в пути или перепланировании игрок получает корректное донесение (Impossible/Contact/обновлённая оценка); вымышленных N/ETA нет, устаревшая оценка не выдаётся за актуальную.
- [ ] Донесение сохраняет четыре поля `§5`, источник и уверенность ≤2 для обычного источника (`§6`), метки времени события/доставки; скрытая истина и неизвестная топология не раскрываются.
- [ ] Одинаковый seed/ввод и загрузка снимка дают те же N/минуты/ETA и порядок донесений (`§12`); новый RNG/новое состояние симуляции не вводятся.
- [ ] Scope/non-scope согласованы; зависимость от правок `rules.md` отсутствует; переданы architect refs на текущий код и сценарии проверки.
