# FS-002 — Разделение отряда

- **Статус:** blocked
- **Источник:** `docs/gameDocs/featureBacklog.md` #1 «Предусмотреть разделение разделение отряда - тогда появлется ещё одно подразделение среди доступных» (опечатка в исходнике сохранена дословно); уточняющий запрос оркестратора (2026-11-20).
- **Связанные правила:** `docs/gameDocs/rules.md §1` (цель сценария и разбор — независимые величины), `§2` (юниты и их атрибуты, командир, выучка/боевой опыт, `PoorControl`), `§3` (действия штаба, курьеры, суперсессия приказов, журнал, порядок событий отрезка), `§4` (закрытые списки слотов/намерений/условий/действий/режимов, A/P), `§5` (четыре стадии приказа), `§6` (четыре поля донесения, `fact key`, знание ≠ истина), `§7` (`CombatEffective`, `InitialStrengthSnapshot`, `PendingCasualties`, тик боя), `§11` (цели, контрольные минуты, AAR), `§12` (инварианты, параметры профиля, детерминизм/seed/replay, сохранение), `§14` (пример тайминга).
- **Связанные артефакты:** `docs/gameDocs/featureSpecs/FS-001-commander-casualty-and-replacement.md` (статус `draft`, прямо предполагает 1:1 «юнит ↔ активный командир» и имеет собственные открытые вопросы); `docs/gameDocs/featureBacklog.md` #7 (составные подразделения — отдельная идея, в данную спеку не входит).
- **Владелец спеки:** analyst

## Цель и ценность
- Дать начальнику штаба механизм получить **дополнительное доступное подразделение из уже имеющегося**, не добавляя «внешнее» подкрепление: split меняет число адресуемых юнитов и, соответственно, число одновременно решаемых задач.
- Сделать размен осмысленным: большее число мелких формирований означает больше независимых приказов/курьерских плеч и большее покрытие района, но каждое из них слабее и уязвимее по `§7`; цена ошибки приказа (`§4`) и тумана войны (`§6`) сохраняется.
- Сохранить инварианты канона: детерминизм/replay и версионированное сохранение (`§12`), слияние донесений и сокрытие истины до разбора (`§6`, `§11`), симметрию сторон (`§2`), отсутствие утечки скрытых полей в UI/AI (`§12`).

## Бизнес-поведение и сценарии

### 0. Факты и отсутствующие данные (из доступных артефактов)
- В бэклоге #1 зафиксирован только результат («ещё одно подразделение среди доступных»). **Не заданы**: инициатор split, момент и фаза разрешения, источник и способ деления ресурсов, правила для командира/черт/эффективного приказа, связь с целями и AAR, критерии приёмки. Догадки вместо этих данных не вносятся — они вынесены в «Открытые вопросы».
- В `rules.md` нет механики разделения: `§3` задаёт действия штаба, `§4` — закрытый список намерений, `§12` — ограниченный набор того, что может менять профиль. Механику нельзя ввести только параметрами профиля без правки канона.
- В текущем коде (snapshot ветки `master` на момент анализа) `Unit` хранит плоский набор ресурсов и одного командира (`CommanderTraits`), `GameState.Units` — плоский словарь по ID; связей «родитель/дочернее формирование», доменного события split и DTO-полей для него нет (`Kriegsspiel.Core/Domain/Unit.cs:27-90`, `Kriegsspiel.Core/Domain/GameState.cs:10`, `Kriegsspiel.Core/Content/Scenario.cs:15`). Код не изменялся.
- FS-001 (`draft`) ещё не закрыла модель командира; её допущение 1:1 конфликтует с появлением второго формирования. Это зависимость, а не решённый факт.
- В бэклоге #1 нет ссылки на `FS-*` и критериев готовности; данные о ранее принятых решениях по этой идее в доступных артефактах отсутствуют — фиксируется как пробел, а не как «нет решений».

### 1. Целевое поведение (бизнес-уровень, проектное, не канон)
- Исходное формирование `P` в минуту `t` порождает новое формирование `C` со **новым стабильным ID**; оба являются юнитами в смысле `§2` и оба присутствуют в `GameState.Units`. `P` продолжает существовать (не «переименовывается»).
- Результат для игрока: `C` становится адресуемым в `ПРИКАЗ`/`ЗАПРОС` («среди доступных») **только по правилам доступности, которые ещё предстоит зафиксировать в каноне** (см. блокеры B1/B7): если split — действие самого игрока, он знает о нём из журнала (`§3`); если split инициирован командиром/событием, факт проходит через донесение (`§5`, `§6`).
- Разделение не равно «созданному подкреплению»: новые люди не появляются, ресурсы `C` должны быть вычтены из `P` по правилам, которые предстоит согласовать (B3). Подкрепления и невидимые резервы по `§7` в `InitialStrengthSnapshot` не включаются; split не должен обходить это ограничение.
- Разделение не создаёт иерархии уровня «полк → батальоны/артиллерия/разведчики»: это отдельная идея #7. В MVP split даёт **два одноуровневых юнита**.

### 3. Сценарии, которые должна покрывать будущая механика
1. **Игрок инициирует split в штабе:** в журнале появляется запись, число доступных адресатов увеличивается; оба формируются в исходной зоне; суммарные ресурсы не превышают исходные (проверка B3); последующий приказ уходит каждому ID отдельно через курьера `§3`.
2. **Split как приказ:** приказ доставляется и понимается по `§3-5`; если канон введёт такую ветку, обязаны быть определены A/P, исходы непонимания и момент появления `C` (B1, B2, B6).
3. **Split во время боя/с отложенными потерями:** обе части участвуют в том же тике `§7`; уже запланированные потери не исчезают; split не даёт обновления готовности или дополнительного броска инициативы (B6).
4. **Split и туман войны:** если инициатор не игрок, появление `C` не становится известно мгновенно; факт проходит через донесение с четырьмя полями (`sourceId`, confidence и др.) по `§5-6`; до этого UI показывает только знание (B7).
5. **Split и цель «сохранить юнит выше X%» / `CombatEffective`:** требуется согласованное правило для `InitialStrengthSnapshot` обеих частей; без него сценарий даёт разный результат в зависимости от момента split (B3).
6. **Replay/save-load:** одинаковый seed и ввод дают одинаковый split, тот же порядок RNG и те же ID; после загрузки снимка доступны обе части, их приказы/эффективные приказы и события (`§12`).

## Scope / Non-scope
- **In scope (предлагаемый MVP после снятия блокировок):**
  - Создание второго одноуровневого юнита с новым ID из существующего, адресуемого в приказах/запросах.
  - Детерминированное деление ресурсов и согласованные значения `InitialStrengthSnapshot`, черт/командирования и выучки для обеих частей (B3, B4).
  - Правила наследования/не-наследования эффективного приказа, позы и вектора внимания (B5).
  - Точная фаза события split в порядке отрезка и взаимодействие с боем/`PendingCasualties` (B6).
  - knowledge-контракт раскрытия, журнал, AAR-строка, параметры профиля/валидация, persistence/replay, симметрия противника (B7-B9).
- **Out of scope (явно):**
  - Обратное слияние/поглощение частей, передача ресурсов между ними и «пере-split» как отдельная механика (может появиться позже отдельной фичей).
  - Составные подразделения и иерархия «полк → батальоны + приданная артиллерия + разведчики» — backlog #7.
  - Изменение канона `rules.md` или `AGENTS.md`; декомпозиция в `T-*`; правки `todo.md`, `featureBacklog.md`, `featureSpecs/README.md`, `structure.md`.
  - Детальные формулы/баланс, пока не сняты блокировки B1-B9 (в спеке фиксируются только инварианты и требования к ним).
