# FS-016 — Поиск по зонам

- **Статус:** ready_for_decomposition
- **Источник:** `docs/gameDocs/featureBacklog.md` #19 «Нужен какой-то поиск по зонам, сейчас приходится скроллить длинный список»
- **Связанные правила:** `docs/gameDocs/rules.md §3` (`КАРТА`/`ЗАПРОС` как разные действия штаба; `QuerySent`/`QueryAnswered`/`QuerySilence`, курьеры и ETA), `§4` (зона/объект/ребро как цель приказа — контекст выбора зоны), `§5` (донесение с четырьмя полями; понимание/исполнение не зависят от UI), `§6` (карта показывает только знание; «нет данных» vs «пусто»; уверенность, метки времени, версии; истина доступна только в разборе), `§12` (инварианты, детерминизм, версионированный снимок сохранения). Спека не меняет канон правил.
- **Владелец спеки:** analyst
- **Дата:** 2026-11-20

## Цель и ценность
- Сократить время поиска нужной зоны на большой карте: заменить линейный просмотр длинного списка на локальный фильтр с частичным совпадением.
- Сохранить характер карты как знания (`§6`): поиск ускоряет навигацию, но не меняет знание игрока, не раскрывает скрытую истину и не подменяет внутриигровой запрос донесения (`§3`, `§5`).
- Реализовать инкремент масштабируемой навигации `FS-005` (средство сужения выборки зон) без нового игрового действия и без изменений правил.

## Бизнес-поведение и сценарии

### 1. Природа поиска
- Поиск — **локальная операция интерфейса**: фильтрация уже доступного игроку перечня зон карты по строке запроса. Он не является приказом, запросом юниту/разведке, донесением или событием симуляции.
- Поиск **не создаёт** `QuerySent`/`QueryAnswered`/`QuerySilence`, не занимает курьера, не меняет часы, `EventLog`, `PlayerKnowledge`, RNG-состояние, приказы/эффективные приказы и снимок сохранения (`§3`, `§5`, `§12`). `QueryCommand` остаётся механизмом внутриигрового запроса с доставкой и молчанием; его поведение не переопределяется.
- Результат поиска детерминирован при том же состоянии и той же строке: один и тот же ввод даёт один и тот же набор строк в одном порядке.

### 2. Множество зон для поиска
- Поиск выполняется только по зонам, которые игрок видит в представлении карты (модель графа сценария: `Id`, `Name`, топология/рёбра). Это и есть «известные игроку зоны» в рамках данной фичи.
- Зоны без доставленных донесений **остаются в этом множестве** и отображаются как «нет данных» (`§6`, `FS-005`); поиск по их `Id`/`Name` работает, но не подменяет отсутствие знания на «пусто».
- Скрытые поля истины (`PresentUnitIds`, фактический `ControllingFaction`, состояние/целостность объектов, груз, намерения противника) **не являются источником ключей поиска и не раскрываются в результате**. Источник данных — только доступное игроку знание/`PlayerKnowledge` и уже отображаемые в карте/обстановке атрибуты графа.

### 3. Ключи и правила совпадения
- Ключи поиска: `Id` зоны, `Name` зоны, а также **известные игроку ссылки на объекты** (идентификатор/название объекта), уже присутствующие в доступном игроку знании/представлении: значения и `fact key` доставленных фактов/`PlayerKnowledge` и объекты, явно показанные как часть топологии карты (например, мост/переправа на ребре).
- `Zone.Objects` как сырая истина симуляции **не используется напрямую** как ключ: если объект игроку неизвестен, поиск по нему не должен возвращать зону. Сведения о состоянии/исправности объекта поиск не проверяет и не показывает.
- Совпадение — **частичное (подстрока), без учёта регистра**; строка запроса триммируется по краям; совпадения по разным ключам объединяются (OR). Не требуются токенизация, транслитерация, нечёткий поиск, регулярные выражения и исправление опечаток.
- Порядок результатов стабилен и совпадает с порядком строк карты (по `Id` зоны); дубликаты строк не создаются, даже если совпало несколько ключей одной зоны.
- Пустая или содержащая только пробелы строка запроса означает «без фильтра» и показывает обычный полный перечень зон, а не пустой результат.

### 4. Сценарии использования
1. **Большая карта:** игрок открывает `КАРТА`, вводит часть `Id` (например, `B3`) или часть названия (`Мост`) и получает только подходящие строки; остальной список не прокручивается.
2. **Поиск по известному объекту:** игрок вводит название/Id уже известного ему объекта (например, мост, показанный в топологии или фиксированный доставленным донесением) — результатом становится зона, связанная с этим объектом в доступном знании. По неизвестному объекту результат пуст.
3. **Туман войны:** зона без донесений находится по `Id`/названию и показывается как «нет данных» с 0/3 уверенности; поиск по названию скрытого объекта не раскрывает истину о зоне.
4. **Пустой результат:** при отсутствии совпадений выводится явное сообщение «ничего не найдено», без строк таблицы; игрок может сбросить/изменить запрос и вернуться к полному обзору. Пустой результат поиска не означает «пустой район» (`§6`).
5. **Планирование приказа:** найденная зона используется как ориентир для существующего выбора цели в `ПРИКАЗ` (`§4`); поиск сам по себе цель приказа не заполняет и не отправляет.

### 5. Интеграция со списком/картой
- Поиск встраивается в экран `КАРТА` и применяется к тому же перечню зон, который уже рендерится в таблице карты (`MapRenderer`/`MapCommand`). Фильтруются строки перечня, а не создаётся второй независимый «результатный» список с иной семантикой.
- Все обязательные элементы знания `§6` в строке результата сохраняются: состояние (`нет данных`/`пусто`/`занято`), «кто по донесениям», уверенность, время события и время доставки/обновления, все версии при противоречии. Скрытие колонок ради компактности поиска недопустимо.
- Если в рамках `FS-005` реализован режим фокуса/детали зоны, выбор найденной строки должен переводить в этот режим для той же зоны; возврат к обзору и сброс поиска остаются доступными. При отсутствии фокуса поиск остаётся фильтром обзора.
- Минимальное переиспользование в смежном перечне (`ОБСТАНОВКА`/`SituationCommand`) допускается только через ту же проекцию доступного знания и без изменения его семантики (в т.ч. строки «прочие зоны (N)»); самостоятельная переработка этих экранов — вне scope.
- Новый пункт верхнего меню штаба не требуется; поиск — часть уже существующего действия `КАРТА` (`§3`, `GameLoop`).

## Scope / Non-scope
- **In scope:**
  - Локальный консольный поиск/фильтр по перечню зон карты по `Id`, `Name` и известным игроку ссылкам на объекты, с частичным совпадением без учёта регистра.
  - Интеграция поиска в существующий рендер карты/перечень зон, сохранение всех элементов знания `§6` и стабильного порядка строк.
  - Явное поведение при пустой строке (полный список) и при отсутствии совпадений (сообщение + сброс), без изменения состояния симуляции.
  - Связка найденной строки с режимом обзора/детали `FS-005` в объёме навигации, без изменения правил выбора целей приказов.
  - Проверяемые сценарии 1–5 и отсутствие утечки скрытой истины в результатах поиска.
- **Out of scope:**
  - Изменения `docs/gameDocs/rules.md`, `AGENTS.md`, `todo.md`, игровых механик, баланса, детерминизма симуляции и тумана войны.
  - Внутриигровой запрос (`QueryCommand`, `QuerySent`/`QueryAnswered`/`QuerySilence`), курьеры, донесения, журнал, RNG и сохранение/replay как объекты изменения: поиск не должен их затрагивать.
  - Поиск по скрытым полям истины (фактические юниты в зоне, контроль, состояние/целостность объектов, груз) и по зонам вне доступной карты сценария.
  - Нечёткий/транслитерационный/регулярный поиск, ранжирование по релевантности, подсветка совпадений как обязательное требование, автодополнение.
  - Полная переработка UX приказов, журнала, обстановки, графика/сети и обязательные координаты зон; новые игровые сценарии (кроме тестовых/демо-данных для проверки).
  - Локализация как отдельная фича (`FS-009`): поиск использует уже отображаемые локализованные подписи и стабильные ID; новая семантика перевода не вводится.

## Разрешённые неоднозначности и решения
- **Вопрос:** Это новый внутриигровой «запрос» или локальный поиск по уже показанному списку?
  - **Решение:** Локальный поиск в `КАРТА`. Он не отправляет `QuerySent`, не занимает курьера и не порождает донесения; `QueryCommand` сохраняет свою роль внутриигрового запроса.
  - **Основание:** `rules.md §3` различает `КАРТА` (просмотр знания) и `ЗАПРОС` (передача курьером); `§5` описывает донесение как результат стадий приказа, а не как реакцию на нажатие клавиши; `§12` запрещает изменение инвариантов профилем.
- **Вопрос:** Что считать «известной игроку зоной» для поиска?
  - **Решение:** Множество зон, доступных в текущем представлении карты (граф/топология сценария по `§1`, `§2`). Зоны без данных остаются доступными как «нет данных». Поиск не оперирует скрытыми полями истины и не добавляет зон вне карты.
  - **Основание:** `rules.md §6` требует различать «нет данных» и «пусто» и показывать карту как знание; `FS-005` требует масштабируемой навигации по всему перечню зон, включая «нет данных». Ограничение поиска только зонами с `HasZoneData` скрыло бы часть обзора и противоречило бы `§6`/`FS-005`.
- **Вопрос:** Как понимать «известные объекты» в качестве ключа, если отдельной модели знания об объектах нет?
  - **Решение:** Ключом является идентификатор/название объекта только тогда, когда ссылка на него уже доступна игроку: в доставленных фактах/версиях `PlayerKnowledge` или в показанной топологии (мост/переправа). Сырые `Zone.Objects` (и их состояние/целостность/контроль) как источник совпадений не используются; неизвестный объект даёт пустой результат. Вводится только фильтрация по уже доступным данным, без новой модели знания об объектах.
  - **Основание:** `rules.md §6` (знание ≠ истина; истину показывает разбор), `§2` (объекты зон как часть мира), текущая модель `PlayerKnowledge` (есть знание зон/фактов, нет отдельной модели знания об объектах) и `FS-005` (запрет усиливать раскрытие скрытой информации).
- **Вопрос:** Каким должно быть частичное совпадение?
  - **Решение:** Подстрока без учёта регистра по каждому из ключей, с триммингом запроса и OR-объединением; стабильная сортировка по `Id` зоны. Пустая строка = без фильтра. Нечёткость/опечатки/регулярки не поддерживаются.
  - **Основание:** формулировка backlog #19 и требование проверяемости; соответствие текущему порядку строк `MapRenderer` и ограничениям `§12` (детерминизм, без RNG).
- **Вопрос:** Что показать при отсутствии совпадений?
  - **Решение:** Явное сообщение «ничего не найдено», ноль строк результата, доступные сброс/возврат к полному обзору. Состояние симуляции и знание не меняются; результат не трактуется как «пустой район».
  - **Основание:** `rules.md §6` (различие «нет данных» и «пусто»), `§3` (просмотр карты не меняет мир).
- **Вопрос:** Нужны ли изменения правил/эскалация к `rules-auditor`?
  - **Решение:** Нет. Фича — презентационная навигация по уже доступному знанию и графу; канон, баланс и игровые механики не меняются.
  - **Основание:** сопоставление с `rules.md §3, §5, §6, §12` и зависимость от `FS-005`.

## Критерии готовности к декомпозиции / приёмки (бизнес)
- [ ] Поиск доступен в экране `КАРТА`, применяется к тому же перечню зон, что и карта, и не создаёт отдельный список с иной семантикой.
- [ ] Полное и частичное совпадение по `Id`/`Name` зоны работает без учёта регистра; порядок результатов стабилен и совпадает с порядком карты; дубликатов нет.
- [ ] Поиск по известной игроку ссылке на объект возвращает связанную зону; поиск по неизвестному/скрытому объекту возвращает пустой результат и не раскрывает скрытые поля зоны/объекта.
- [ ] Зоны без донесений остаются в перечне как «нет данных» и находятся по `Id`/`Name`; в строке результата сохранены состояние, «кто по донесениям», уверенность, время события/доставки и версии противоречий по `§6`.
- [ ] Пустая/пробельная строка показывает полный перечень; отсутствие совпадений даёт явное сообщение и сброс, а не «пустой район».
- [ ] Поиск не меняет часы, RNG, `PlayerKnowledge`, курьеров, приказы, донесения, `EventLog` и сохранение; `QueryCommand` и контракт `QuerySent`/`QueryAnswered`/`QuerySilence` не изменены (`§3`, `§5`, `§12`).
- [ ] Scope/non-scope зафиксированы; зависимость от правок `docs/gameDocs/rules.md` отсутствует; открытых вопросов нет.

- **Риски/ограничения:** не допустить утечки `Zone.Objects`/`PresentUnitIds`/`ControllingFaction` через результаты поиска; не смешивать поиск с `QuerySent` и курьерской моделью; не создавать RNG/состояние, чтобы не задеть `§12`; учесть `FS-009` (подписи локализуются, ID стабильны).
