# Workflows и промпты (оркестрация разработки)

Каталог описывает **процессы** и **готовые промпты** для оркестрации работы агентов/людей над задачами репозитория.

## Содержание
- `task-lifecycle.md` — жизненный цикл задачи и волны, роли, ветвление, входы/выходы, переходы.
- `prompts/` — шаблоны промптов (копировать в чат/issue/таск-трекер), по этапам.

## Принципы
- Единый источник истины по плану: `docs/projectDocs/todo.md`. Игровые идеи: `docs/gameDocs/featureBacklog.md`. **`todo.md` правится только в отдельной ветке по специальному запросу**; правки вносит только `architect` (по запросу `orchestrator`). `implementer`, `verifier`, `scenario-tester` и другие исполнители `todo.md` не правят.
- Находки вне задачи фиксируются в `docs/projectDocs/tech-debt.md` (активные `open`/`planned`), закрытые — по политике очистки/архивации (`tech-debt-archive.md`).
- Перед началом работы читать `AGENTS.md`, при необходимости `docs/gameDocs/rules.md`, `instructions.md`, `structure.md`.
- Изменения в `AGENTS.md`, `docs/gameDocs/rules.md` — только по отдельному явному запросу.
- Коммиты — только по явной просьбе пользователя (если иначе явно не согласовано в задаче).
- Код без лишних комментариев, если явно не просили.
- **Изменения процесса не имеют обратной силы:** новые правила применяются к новым задачам, волнам и отчётам; существующие артефакты не приводятся задним числом к обновлённому виду.

## Модель исполнения
- **Gate проверяемости (до старта):** до начала работ по волне `verifier` оценивает достаточность формальных описаний проверок для волны и её задач. Если описаний недостаточно, `verifier` эскалирует `orchestrator`, работы по волне не начинаются (ветка волны не создаётся, задачи не запускаются) до доработки плана `architect`. `orchestrator` и каждый исполнитель перед началом своей части также проверяют наличие/понятность проверок и при проблемах эскалируют.
- **`orchestrator`** — координатор: волны, проверки зависимостей/ownership, gate проверяемости, запуск ролей, сбор артефактов, эскалации.
- **`architect`** — декомпозиция и правки плана в `todo.md` (в отдельной ветке по спецзапросу), описание **сценария проверок волны**, triage/анализ причин падений сборки и тестов, постановка корректирующих `T-*`. Не реализует код и не выполняет merge.
- **`implementer`** — реализация одной `T-*` в своей ветке задачи, проверки в ветке, MR в ветку волны, структурированный ввод для `verifier`.
- **`verifier`** — per-task верификация, merge задач в ветку волны после `verified`, проверка/финализация отчётов задач (коммит отчётов после прохождения проверок), wave-проверка по сценарию `architect`, формирование/коммит wave-report, merge ветки волны в основную ветку при выполнении условий. При сбоях не исправляет код/тесты, эскалирует на `architect`.
- **`scenario-tester`** — воспроизводимые прогоны и ввод для wave-проверки/отчёта по запросу оркестратора.
- Параллельные запуски `implementer` в волне допустимы только при отсутствии пересечений `Владеет файлами`.

## Ветвление (обязательно)
1. **До старта волны:** `verifier` проводит gate проверяемости — подтверждает достаточность формальных описаний проверок для волны (сценарий) и всех её `T-*` (`Как проверить`, `Готово, если`). При недостаточности — эскалация `orchestrator`, доработка `architect`, **ветка волны не создаётся и задачи не запускаются**.
2. После прохождения gate по команде `orchestrator` `architect` создаёт **ветку волны** `wave/<N>-<slug>` от базы, указанной оркестратором (обычно `main`). `todo.md` правится `architect` в отдельной ветке по спецзапросу; до старта работ по волне `orchestrator` обеспечивает попадание актуального плана/сценария волны в базу или ветку волны (merge/обновление). При изменении плана в ходе волны ветка волны и затронутые task-ветки синхронизируются до следующих раундов/merge по решению `orchestrator`.
3. Для каждой задачи `implementer` создаёт ветку `task/T-XX-<kebab-slug>` **от ветки волны**.
4. MR задач нацеливаются в **ветку волны** (не в `main`). `verifier` выполняет merge задачи в ветку волны **только после `verified`** по данной задаче, после чего проверяет сборку/старт в контексте ветки волны. При отсутствии технических прав на merge: `verifier` фиксирует `ready to merge`, коммитит/подготавливает отчёт со статусом; `orchestrator` назначает исполнителя merge, после фактического merge подтверждаются пост-merge проверки и `verifier` актуализирует/подтверждает финальное состояние отчёта (задача не `done` до этого).
5. Циклы замечаний проходят в ветке задачи до её влития в ветку волны.
6. После влития всех задач волны `verifier` выполняет **проверки волны на ветке волны** по сценарию, описанному `architect` при декомпозиции. При необходимости проводятся корректирующие циклы (новые/доработанные задачи по процессу).
7. После успешного прохождения всех условий ветка волны мержится в `main` (`verifier` или назначенный `orchestrator` исполнитель при отсутствии прав; при этом wave-условия подтверждены). Отчёт волны коммитится в ветке волны после прохождения проверок и попадает в `main` вместе с merge ветки волны. Прямые коммиты в `main` запрещены. `verifier` коммитит файлы `docs/projectDocs/reports/**` в ветке волны в рамках роли; при отсутствии прав на коммит — передаёт финальное содержимое отчёта и коммит выполняет назначенный оркестратором исполнитель до завершения шага.

## Проверки и валидация
- **Строго по одной задаче (`T-XX`)**: верификация, `verified` и merge в ветку волны — отдельно для каждой задачи; batch запрещён.
- **`implementer`** запускает автотесты/проверки из `Как проверить` в своей ветке до передачи на верификацию и предоставляет структурированный ввод. При невозможности прогона — `blocked`/ограничение с доказательствами.
- **`verifier`** не исправляет код/тесты при сбоях: фиксирует факты, логи/команды, scope и эскалирует на `architect`.
- **Сценарий проверок волны** (задаёт `architect` при декомпозиции, обязательно в карте волн/плане): общие проверки работоспособности + конкретные проверки **добавленных или изменённых** механик. Если механики не добавлялись и не менялись — явно «достаточно проверки факта сборки и запуска» (если не указано иное). `verifier` следует сценарию; при неясности границ — эскалация, не ad-hoc расширение.
- **Корректирующие задачи после проблем на волне:** `architect` анализирует причины и разбивку по задачам волны. Обоснование фиксируется в corrective `T-*` в `todo.md` и в `wave-*-report.md` (маппинг «причина/затронутые T-* → корректирующая T-*»). Разные причины — несколько задач и при необходимости несколько `implementer`. Одна причина с пересекающимся ownership — одна задача (последовательно/интеграционная волна). При падении автотестов по умолчанию — одна задача на инцидент/причину; разбиение — при явно разных причинах/привязке к разным задачам волны.

## Отчёты и временные артефакты
- Канонический владелец отчётов в `docs/projectDocs/reports/` — **`verifier`**. `verifier` коммитит файлы отчётов в ветке волны **после прохождения проверок** (допустимое исключение из запрета коммитов не в ветке задачи): task-report — после per-task проверок (при `ready to merge` с последующей актуализацией); wave-report — после wave-проверок, в ветке волны.
- `implementer` готовит структурированный ввод во временном файле `docs/projectDocs/reports/.tmp/implementer-T-XX-r<N>.md` (`N` — номер раунда), удаляет его **перед передачей результатов на проверку**. При доработке создаёт новый файл следующего раунда и также удаляет перед передачей. Содержимое `.tmp/*` (кроме `README.md`) игнорируется git; временные файлы не коммитятся.
- `verifier` формирует **отчёт по волне** при проверке после влития всех задач волны, на основе сценария проверок `architect` и фактических результатов (включая `## Ретро процесса`).
- Шаблоны и правила процессного лога: `docs/projectDocs/reports/README.md`. Процессные фрикции — в отчётах; продуктовые/кодовые находки вне scope — в `tech-debt.md` (`TD-*`).

## Рекомендуемый порядок
1. `orchestrator` формирует цель и контекст; при необходимости запускает `architect` (декомпозиция/план, сценарий проверок волны) с учётом `tech-debt.md`.
2. `architect` готовит/обновляет `todo.md` в отдельной ветке по спецзапросу.
3. **Gate проверяемости:** `verifier` подтверждает достаточность описаний проверок для волны и задач. При недостаточности — доработка `architect` по запросу `orchestrator`; до прохождения gate ветка волны не создаётся и задачи не запускаются.
4. После gate: создание ветки волны и параллельный запуск `implementer` (без пересечений ownership): ветка задачи от ветки волны → проверки в ветке → ввод в `.tmp` → удаление `.tmp` → передача на проверку → MR в ветку волны.
5. `verifier` проверяет каждую задачу отдельно, мержит в ветку волны после `verified`, проверяет сборку/старт, коммитит task-report после проверок. При замечаниях — итерации `implementer` в той же ветке задачи.
6. После всех задач `verifier` выполняет wave-проверки на ветке волны, формирует/коммитит wave-report и мержит ветку волны в `main` при выполнении условий. При сбоях — анализ `architect` и корректирующие задачи с учётом разбивки причин.
7. При изменениях структуры — `docs-maintainer` обновляет `structure.md`.
