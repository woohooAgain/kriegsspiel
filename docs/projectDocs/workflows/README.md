# Workflows и промпты (оркестрация разработки)

Каталог описывает **процессы** и **готовые промпты** для оркестрации работы агентов/людей над задачами репозитория (неспецифичные имена ролей и скиллов).

## Содержание
- `task-lifecycle.md` — жизненный цикл задачи от бэклога до закрытия, роли, входы/выходы, переходы.
- `prompts/` — шаблоны промптов (копировать в чат/issue/таск-трекер), по этапам.

## Принципы
- Единый источник истины по плану: `docs/projectDocs/todo.md` (исполняемые карточки/план). Игровые идеи: `docs/gameDocs/featureBacklog.md`.
- Находки вне задачи фиксируются в `docs/projectDocs/tech-debt.md` (планировщик читает перед декомпозицией).
- Перед началом работы по задаче/декомпозиции читать `AGENTS.md`, при необходимости `docs/gameDocs/rules.md`, `instructions.md`, `structure.md`.
- Изменения в `AGENTS.md`, `docs/gameDocs/rules.md` — только по отдельному явному запросу, если не оговорено иначе.
- Коммиты — только по явной просьбе пользователя (если иначе явно не согласовано в задаче).
- Код без лишних комментариев, если явно не просили.

## Модель исполнения (важно)
- **Оркестратор** — координатор: выбирает волну, проверяет зависимости и непересечение `Владеет файлами`, формирует пакеты запуска, собирает артефакты и принимает решения о переходах. Оркестратор **не обязан** выполнять тяжёлую реализацию/проверки «в одном контексте» вместо делегирования.
- **Роли в промптах** — инструкция для **одного запуска** агента/сабагента под эту роль. Один запущенный агент **не должен** неявно подменять все роли; разделение по умолчанию: отдельные запуски `planner`, `implementer`, `verifier`, при необходимости `scenario-tester`, `rules-auditor`, `docs-maintainer`, `repo-navigator`.
- **Параллелизм**: в рамках одной волны **несколько запусков `implementer`** могут идти параллельно **только** если у их `T-*` нет пересечений по `Владеет файлами`. Любое пересечение — стоп, перераспределение по волнам или перепланирование.
- **Декомпозиция параллельно с реализацией**: запуск `planner` допустим параллельно с активной реализацией **только** если план не меняет файлы/ветки активной волны и результат не вливается в `todo.md` без явной проверки оркестратором на конфликты; иначе — последовательно.

## Git и поставка изменений (обязательно)
- **Запрещено коммитить в `main`** (и в целевую ветку интеграции напрямую). Рабочие коммиты агентов — **только в ветке задачи** `task/T-XX-<kebab-slug>`, созданной от базы, указанной оркестратором (обычно `main` или оговорённая интеграционная ветка). `implementer` и другие роли не делают merge в `main`/целевую ветку.
- По готовности к проверке `implementer` подготавливает **MR/PR** в целевую ветку, указанную оркестратором, и фиксирует ссылку/ID и список изменений в отчёте (`docs/projectDocs/reports/`).
- **`verifier` всегда выполняет merge MR в целевую ветку после статуса `verified`** (после выполнения пунктов `Готово, если`, проверок из `Как проверить` и требуемых тестов/прогонов по карточке). Если технически выполнить merge нельзя (нет прав/доступа) — `verifier` оставляет пометку **`ready to merge`** в отчёте с причиной и ссылкой на MR; оркестратор назначает исполнителя merge, но **готовность к merge определяется верификацией `verifier`**.
- После каждого merge в целевую ветку **обязательно** проверять, что проект **собирается и стартует** (канонические команды из `instructions.md`/карточки и запуск приложения по репозиторию). Результат фиксируется в отчёте задачи и/или волны.
- **После выполнения всех задач волны** проводится **полноценное тестирование: запуск и игра** (интеграционный прогон по сценариям/чеклисту); оркестратор с участием `scenario-tester`. Итоги — в отчёте волны (`docs/projectDocs/reports/wave-*-report.md`) и при необходимости в `tech-debt.md`.

## Рекомендуемый порядок (кратко)
1. Оркестратор выбирает вход: пункт из `featureBacklog.md` или запрос → при необходимости запускает **планировщика** (декомпозиция) с учётом `tech-debt.md` (см. «Модель исполнения»).
2. Получает/обновляет карточки в `todo.md` по `docs/projectDocs/templates/taskDecompositionTemplate.md`.
3. По волнам: оркестратор выдаёт отдельные запуски `implementer` на задачи волны (параллельно, если ownership не пересекается). Каждый работает в ветке `task/T-XX-<kebab-slug>`, готовит MR; циклы **implementer ↔ verifier** идут до `verified`.
4. После `verified` по задаче **`verifier` выполняет merge MR** в целевую ветку, затем проверяет **сборку и старт**; при проблемах — `blocked` или новый раунд по решению оркестратора. Отчёт по задаче — в `docs/projectDocs/reports/` (при необходимости).
5. После завершения всех задач волны и post-merge проверок проводится **полноценное интеграционное тестирование: запуск и игра**; результаты — в отчёте волны `docs/projectDocs/reports/wave-*-report.md`.
6. Финальная сверка документации: при изменениях структуры — `docs-maintainer` обновляет `structure.md`.
