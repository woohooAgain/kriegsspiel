# Workflows и промпты (оркестрация разработки)

Каталог описывает **процессы** и **готовые промпты** для оркестрации работы агентов/людей над задачами репозитория.

> **Source of truth:** канонические определения ролей — `.opencode/agent/*`, стандарты/шаблоны/чек-листы — `.opencode/skills/*`, лончеры ролей — `.opencode/command/*`, глобальные инварианты — `AGENTS.md` + скилл `process-contract`. Этот каталог — человекочитаемый обзор; при расхождении приоритет у `.opencode`/`AGENTS.md`.

## Содержание
- `task-lifecycle.md` — жизненный цикл задачи/волны/фичи, роли, ветвление, входы/выходы, переходы.
- Шаблоны промптов заменены стандартными артефактами opencode (см. `.opencode/agent`, `.opencode/command`).

## Маршрутизация заметок (intake)
Один вход → один канонический артефакт; между артефактами только ссылки, без копирования тела (анти-дублирование).

| Тип заметки | Куда писать (канон) | Владелец/триаж | Дальше |
|---|---|---|---|
| Новая фича / идея / «хотим уметь» | `docs/gameDocs/featureBacklog.md` (`BL-*`) | `analyst` (caretaker/groomer) | `FS-*` → `architect` → `T-*` |
| Требования/поведение новой фичи | `docs/gameDocs/featureSpecs/FS-*` | `analyst` | `ready_for_decomposition` → `architect` |
| Баг / доработка **существующей** реализации (вне текущего scope) | `docs/projectDocs/tech-debt.md` (`TD-*`, `Тип: bug\|improvement\|debt`) | вносит любой; триаж `architect` | `planned` → `T-*` |
| Замечание, **блокирующее текущую** `T-*`/волну | в рамках задачи / triage | `implementer` → `architect` | исправить в задаче или корректирующая `T-*` |
| Процессное трение/мера | `reports/**` раздел «трение» → `PI-*` | `process-master` | `PI-*` |
| Неоднозначность правил | `FS-*` «Открытые вопросы» → `analyst`/`rules-auditor` | `analyst` | решение (без правки `rules.md` без запроса) |

Дерево решений:
1. Про **как мы работаем** (роли/процесс/gate/merge/шаблоны)? → отчёт «трение» → `PI-*` (`process-master`).
2. **Новая возможность**, которой ещё нет? → `featureBacklog.md` (`BL-*`) → `analyst` → `FS-*`.
3. **Дефект/пробел/улучшение уже реализованного** поведения вне текущего scope? → `TD-*` с `Тип: bug|improvement` → `architect` → `T-*`.
4. **Мешает закрыть текущую** `T-*`/волну? → чинить в задаче или triage `architect` → корректирующая `T-*`.
5. **Неоднозначность правил**? → `FS-*` «Открытые вопросы» → `analyst`/`rules-auditor` (канон `rules.md` не меняется без запроса).

Разграничение: `PI-*` — только про то, *как работает команда*; `TD-*` — про *продукт/код/доки* вне текущей задачи, включая баги/доработки реализованного; `BL-*`/`FS-*` — про *новые возможности*.

## Принципы
- **Операционная модель:** конкретные действия выполняют конкретные агенты (читают файлы, анализируют, готовят артефакты). При невозможности разрешить проблему внутренними силами — эскалация с фактами и остановка в своей зоне. `orchestrator` только дирижирует (передаёт refs/цель/ограничения, фиксирует переходы) и в выводе показывает **только статусы/короткие репорты** (Status Envelope) от субагентов; файлы не читает, детали не выводит.
- **File-first handoff:** детали (спеки, планы, проверки, логи, замечания, фрикции, причины) живут в артефактах ветки/репозитория; в чат/оркестратору — только Status Envelope + refs. Полные логи/диффы/копипасты в ответы запрещены; на доработках — дельта.
- **Единый источник истины по плану:** `docs/projectDocs/todo.md`. **`todo.md` правится только в отдельной ветке по специальному запросу**; правки вносит только `architect` (по запросу `orchestrator`). Другие роли `todo.md` не правят.
- **Фичи:** новые идеи — `docs/gameDocs/featureBacklog.md` (`BL-*`, caretaker/groomer `analyst`); бизнес-спеки/готовность к декомпозиции — `docs/gameDocs/featureSpecs/FS-*.md` (готовит `analyst`).
- **Техдолг:** активные `open`/`planned` — `docs/projectDocs/tech-debt.md` (`TD-*` с `Тип: bug|improvement|debt`; без отдельного `BUG-*`-трекера, пока объём мал), закрытые — по политике/архиву. Процессные меры — `docs/projectDocs/process-improvement-log.md` (`PI-*`, `process-master`) и ретро в wave-report, не `TD-*`. Маршрутизация заметок — раздел выше.
- Перед началом работы каждый агент сам читает `AGENTS.md` и релевантные документы (`docs/gameDocs/rules.md`, `instructions.md`, `structure.md`, шаблоны/отчёты) в объёме своей роли; `orchestrator` не читает файлы.
- **Командная гигиена и refs (PI-018/PI-019):** `workdir` вместо `cd`; файлы — `read`/`grep`/`glob`, shell — для git/dotnet/script; одна команда — одна цель; чужие артефакты читать только по переданному `branch@commit`+путь, без discovery по веткам; нет ref — `blocked`/эскалация.
- Изменения в `AGENTS.md`, `docs/gameDocs/rules.md` — только по отдельному явному запросу.
- Коммиты — только по явной просьбе пользователя/правилу роли в рамках процесса (отчёты `verifier`, handoff/код в ветке задачи `implementer` при разрешении). Прямые коммиты в `main` запрещены.
- **Атрибуция коммитов:** все коммиты/merge выполняются с identity роли (`git -c user.name=<role> -c user.email=<role>@kriegsspiel.local ...`), резерв — trailer `Made-by-Agent: <role>`; канон и проверка — `process-contract` §8. Старые коммиты не переписываются.
- **Изоляция запусков:** каждый коммитящий/меняющий файлы запуск работает в собственном git worktree на собственной ветке; общий primary checkout не переключает HEAD и не коммитит. Канон, идентификация своей ветки и жизненный цикл — `process-contract` §5.1.
- Код без лишних комментариев, если явно не просили.
- **Изменения процесса не имеют обратной силы:** новые правила применяются к новым задачам, волнам, спекам и отчётам; существующие артефакты не приводятся задним числом. При анализе старых артефактов извлекать доступную информацию из любого представления и явно отмечать недостающие данные.

## Status Envelope (для оркестратора)
Короткий ответ любой роли (ориентир ≤10 строк): `ROLE | TARGET | STATUS | ROUND | ARTIFACTS (refs) | NEXT | BLOCKERS | SUMMARY (1-3 строки)`. Детали — в артефактах. Для коммитящих запусков `ARTIFACTS` включает `worktree=<path>` и `branch=<own-branch>@<commit>` (`process-contract` §5.1).

## Модель исполнения (роли)
- **`orchestrator`** — дирижёр: маршрутизация по статусам, запуск ролей, передача refs/цели/ограничений, контроль переходов gate/merge/эскалаций. Не читает файлы, не синтезирует, не выводит детали.
- **`analyst`** — фичи/backlog → бизнес-спеки `FS-*`, готовность к декомпозиции, разрешение неоднозначностей правил/требований для `architect`/`implementer` в рамках существующих `rules.md` (правки канона — эскалация отдельным запросом). Не правит `todo.md`, не декомпозирует в `T-*`.
- **`architect`** — декомпозиция/план в `todo.md` (отдельная ветка по спецзапросу), сценарии проверок волн, launch-план волны (группы параллельности/refs), triage причин падений, корректирующие `T-*`. Не реализует код и не выполняет merge.
- **`implementer`** — реализация одной `T-*` в ветке задачи, проверки в ветке, handoff/артефакты и MR в ветку волны (file-first). Не правит `todo.md`, не мержит.
- **`verifier`** — gate, per-task верификация, merge задач в ветку волны после `verified` (или `ready to merge`), пост-merge проверки, финализация/коммит отчётов после проверок, wave-проверка по сценарию, merge ветки волны в `main` при условиях. Не чинит продуктовый код/тесты.
- **`scenario-tester`** — воспроизводимые прогоны/ввод для wave-проверки (file-first). Не чинит, не мержит.
- **`process-master`** — post-wave анализ проблем/эффективности, меры процесса, `PI-*`/вклад в wave-report, контроль эффекта/циклов и баланса детерминизм/сложность. Не чинит продуктовый код/тесты, не заменяет triage `architect`.
- **`rules-auditor`** — доменный супер-эксперт, финальный источник истины по согласованности и трактовке `docs/gameDocs/rules.md`: аудит, поиск противоречий/пробелов, предложения ребаланса и экспертные заключения (в т.ч. для `analyst` и по эскалациям). `rules.md` не меняет без отдельного явного запроса и подтверждения; подготовка изменений — в отдельной ветке и через MR. Не правит `todo.md`, не реализует продуктовый код.
- **`docs-maintainer`**, **`repo-navigator`** — по назначению; `docs-maintainer` актуализирует `structure.md`.

Параллельные `implementer` допустимы только при отсутствии пересечений `Владеет файлами` (определяет launch-план `architect`).

## Ветвление (обязательно)
- **Изоляция:** каждый запуск создаёт собственный linked worktree (`process-contract` §5.1) и работает только в своей ветке; общий каталог не переключает HEAD и не коммитит. Ветка/коммит запуска возвращаются в `ARTIFACTS`; в чужую ветку не коммитят.
1. **Подготовка фичи (при необходимости):** `analyst` готовит/уточняет `FS-*` до `ready_for_decomposition`; неоднозначности разрешаются/эскалируются.
2. **План/сценарий:** `architect` готовит декомпозицию, сценарий проверок волны и launch-план (в `todo.md`/артефакте плана) в отдельной ветке по спецзапросу.
3. **Gate проверяемости:** `verifier` подтверждает достаточность описаний проверок (задачи + волна). При недостаточности — эскалация до старта (ветка волны не создаётся, задачи не запускаются), доработка `architect`/`analyst` по смыслу.
4. **Ветка волны:** после gate `architect` создаёт `wave/<N>-<slug>` от указанной базы (по команде `orchestrator`). Актуальный план/сценарий доступен в базе/ветке волны до старта.
5. **Задачи:** ветки `task/T-XX-<kebab-slug>` от ветки волны; MR в **ветку волны**. `verifier` мержит после `verified` (или `ready to merge` при отсутствии прав с назначением исполнителя). `implementer` merge не выполняет.
6. **Wave-проверка:** после влития всех задач `verifier` выполняет проверки на ветке волны по сценарию `architect`, формирует/коммитит `wave-*-report.md` (включая вклад `process-master` по процессу). При проблемах — triage `architect` и корректирующие циклы.
7. **Завершение:** merge ветки волны в `main` при условиях (или `ready to merge`). Прямые коммиты в `main` запрещены.
8. **Ретро процесса:** `process-master` анализирует волну, фиксирует `PI-*`/эффект/циклы и обновляет процессные артефакты в рамках полномочий.

## Проверки, handoff и валидация
- **Строго по одной задаче (`T-XX`)**: верификация, `verified` и merge в ветку волны — отдельно; batch запрещён.
- **`implementer`** запускает проверки из `Как проверить` в своей ветке до передачи, сохраняет подробный ввод **файлом** (handoff-артефакт в ветке/рабочем дереве, напр. `docs/projectDocs/reports/handoffs/implementer-T-XX-r<N>.md` или согласованный путь; `.tmp` — только локальный черновик при необходимости) и передаёт Status Envelope + ref (без полных логов). При невозможности — `blocked` с доказательствами в артефакте.
- **`verifier`** читает артефакты/MR сам, не исправляет код/тесты при сбоях, эскалирует на `architect` с фактами (refs). Отчёты финализирует/коммитит после проверок.
- **Сценарий проверок волны** (задаёт `architect`, обязателен): общие проверки + проверки добавленных/изменённых механик; иначе явно «достаточно сборки и запуска» (если не указано иное). Граница — перечисление в сценарии.
- **Корректирующие задачи:** `architect` фиксирует причины и маппинг «причина/затронутые T-* → корректирующая T-*» с обоснованной разбивкой (разные причины — разные задачи/при необходимости разные implementer; одна причина с пересекающимся ownership — одна задача).

## Отчёты и артефакты
- Канонический владелец отчётов в `docs/projectDocs/reports/` — **`verifier`** (коммит после прохождения проверок). Подробности процесса/качества handoff — file-first; в коммуникации — статусы.
- Шаблоны/правила: `docs/projectDocs/reports/README.md`. Процессные фрикции и меры — в отчётах/`process-improvement-log.md`; продуктовые находки — в `tech-debt.md`.

## Рекомендуемый порядок
1. `orchestrator` получает цель → маршрутизирует к `analyst` (если нужна спека/уточнение) и/или `architect` (декомпозиция/план). Передаёт refs/ограничения, собирает Status Envelope.
2. `analyst` публикует `FS-*` (`ready_for_decomposition` или `blocked`) → оркестратор передаёт ref `architect`.
3. `architect` готовит `todo.md`/сценарий/launch-план (отдельная ветка по спецзапросу) → Status Envelope.
4. `verifier` проводит gate → `gate passed/failed` (refs на пробелы).
5. После gate `architect` создаёт ветку волны; `orchestrator` запускает `implementer` по launch-плану (без пересечений ownership). Цикл per-task: handoff → `verifier` → merge/report → при сбое triage `architect`.
6. `verifier` выполняет wave-проверки, формирует/коммитит wave-report (с вкладом `process-master`) и мержит ветку волны при условиях.
7. `process-master` проводит ретро, обновляет `process-improvement-log.md`/процессные описания (в рамках полномочий) и сообщает статус; при изменениях структуры — `docs-maintainer`.
