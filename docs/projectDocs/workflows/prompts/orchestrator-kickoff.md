# Промпт: запуск цикла (orchestrator)

Роль: `orchestrator`  
Язык ответа: русский (если не указано иное).

## Вход
- Цель: (одним абзацем)
- Источник: `docs/gameDocs/featureBacklog.md` пункт … / свободный запрос / …
- Ограничения: (что нельзя менять: например `AGENTS.md`, `docs/gameDocs/rules.md`)
- Текущая волна/контекст: (если есть)
- Целевая ветка для MR/merge (например `main` или интеграционная ветка волны): …

## Задача
1. Свериться с `AGENTS.md`, `docs/projectDocs/instructions.md`, `docs/projectDocs/structure.md`, `docs/projectDocs/workflows/README.md`, `task-lifecycle.md`.
2. Определить, нужен ли этап декомпозиции (`planner`). Если да — выдать промпт для `planner` по `prompts/planner-decompose.md`. При запуске `planner` параллельно с активной реализацией явно предупредить о рисках конфликтов с `todo.md`/файлами.
3. Если карточки `T-*` уже есть в `docs/projectDocs/todo.md`, выбрать следующий шаг по волнам.

## Режим параллелизма (обязательно)
4. Для выбранной волны перечислить задачи `T-*` и их `Владеет файлами`. Построить проверку непересечений: **никакой путь/область владения не должна пересекаться** между задачами, которые планируется выполнять параллельно. Если пересечения есть — **не запускать параллельно**, перенести часть задач в следующую волну или перепланировать.
5. Для **каждой** параллельной задачи выдать **отдельный пакет запуска `implementer`** (отдельный промпт/сообщение) на основе `prompts/implementer-take-task.md`, с подстановкой: `T-XX`, целевая ветка MR, требуемое имя/конвенция ветки задачи (например `task/T-XX-...`), ссылки на релевантные разделы `docs/gameDocs/rules.md §…`, напоминание: только ownership, не мержить в main.
6. Запрещено назначать одному запуску `implementer` две задачи волны с пересекающимся ownership и запрещено просить «сделать всё волной» в одном запуске, если это нарушает изоляцию.

## Цикл верификации и вливание
7. После получения отчётов от `implementer`(ов): для каждой задачи запустить `verifier` отдельно по `prompts/verifier-review.md` (привязка к `T-XX`, отчёту, MR/ветке, раунду). При `changes requested` сформировать пакет замечаний и запустить **новый** `implementer` для той же `T-XX` (итерация). Повторять до `verified` или `blocked`.
8. **Только после `verified`** `verifier` **всегда выполняет merge MR** в целевую ветку (если есть права). Сразу после merge — проверка **сборка и старт**. Если merge невозможен технически — `verifier` пишет в отчёт `ready to merge` + причина, оркестратор назначает исполнителя merge; готовность к merge уже зафиксирована `verifier`. При сбое сборки/старта — `blocked` или доработка новым раундом.
9. Требовать от исполнителей фиксацию артефактов в `docs/projectDocs/reports/` (отчёт задачи по шаблону; отчёт волны после пункта 10).
10. После завершения **всех задач волны** организовать **полноценное тестирование: запуск и игра** (`scenario-tester`), оформить отчёт волны в `docs/projectDocs/reports/wave-<N>-report.md`; дефекты → новые `T-*` или `tech-debt.md`.

## Итог
Оформить списком: «Следующие запуски…», «Артефакты на вход», «Ожидаемые выходы (в т.ч. файлы в `reports/`)», «Критерии перехода» (merge выполняет только `verifier` после `verified`, затем post-merge сборка+старт, затем wave-level).

## Ограничения
- Не предлагать менять `AGENTS.md` и `docs/gameDocs/rules.md` без отдельного явного запроса пользователя.
