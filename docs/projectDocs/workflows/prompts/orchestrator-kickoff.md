# Промпт: запуск цикла (orchestrator)

Роль: `orchestrator`  
Язык ответа: русский (если не указано иное).

## Вход
- Цель: (одним абзацем)
- Источник: `docs/gameDocs/featureBacklog.md` пункт … / свободный запрос / …
- Ограничения: (что нельзя менять: например `AGENTS.md`, `docs/gameDocs/rules.md`)
- Текущая волна/контекст: (если есть)
- База для ветки волны / основная ветка: (например `main`)

## Задача
1. Свериться с `AGENTS.md`, `docs/projectDocs/instructions.md`, `docs/projectDocs/structure.md`, `docs/projectDocs/workflows/README.md`, `task-lifecycle.md`.
2. Определить, нужен ли `architect`: декомпозиция/правка `todo.md`, создание ветки волны и сценария проверок волны, triage после падений. При необходимости выдать промпт по `prompts/architect-decompose.md`. **`todo.md` правится только в отдельной ветке по специальному запросу и только `architect`**; остальные роли план не правят.
3. Если карточки `T-*` уже есть в `todo.md`, выбрать следующий шаг по волнам.

## Gate проверяемости (обязательно, до старта работ по волне)
4. **До создания ветки волны и запуска задач** запустить `verifier` в режиме gate (`prompts/verifier-review.md`, режим C): проверить наличие и достаточность формальных способов проверки факта выполнения для волны (сценарий проверок) и для каждой `T-*` (`Как проверить`, `Готово, если`). `orchestrator` и каждый исполнитель своей части также проверяют проверяемость своего объёма.
5. При недостаточности описаний (в т.ч. нет сценария/проверок волны) — **не создавать ветку волны и не запускать задачи**. Отправить план на доработку `architect` (в отдельной ветке по спецзапросу), обеспечить попадание обновлений в актуальный план/базу волны и повторить gate до `gate passed`.

## Ветвление волны
6. После `gate passed` по команде оркестратора `architect` создаёт ветку волны `wave/<N>-<slug>` от указанной базы. `todo.md` правится `architect` в отдельной ветке по спецзапросу; до старта работ актуальный план/сценарий волны должен быть доступен в базе или ветке волны (merge/обновление — обеспечить), после чего временная ветка правки плана удаляется (если не нужна для других целей). При изменении плана в ходе волны синхронизировать ветку волны и затронутые task-ветки до следующих раундов/merge. Ветки задач `task/T-XX-<kebab-slug>` создаются **от ветки волны**; MR задач — в **ветку волны**.

## Режим параллелизма (обязательно)
7. Для выбранной волны перечислить `T-*` и их `Владеет файлами`. Параллельно запускать только задачи без пересечений ownership; при пересечениях — перераспределить по волнам/перепланировать.
8. Для каждой задачи выдать отдельный пакет запуска `implementer` (`prompts/implementer-take-task.md`): `T-XX`, ветка волны (база), ветка задачи, целевая ветка MR = ветка волны, ссылки на `docs/gameDocs/rules.md §…`, напоминания: перед стартом проверить формальные способы проверки своей части, только ownership, проверки/тесты в своей ветке, временный ввод в `docs/projectDocs/reports/.tmp/implementer-T-XX-r<N>.md` с удалением перед передачей на проверку, не править `todo.md`, не мержить.

## Цикл верификации и merge задач (строго по одной задаче)
9. После передачи результатов `implementer` запустить `verifier` **отдельно для каждой `T-XX`** (per-task). Batch-валидация/merge запрещены.
10. При `changes requested` — новый запуск `implementer` той же `T-XX` в той же ветке (следующий раунд, новый `.tmp` файл с удалением перед передачей). Повторять до `verified`/`blocked`.
11. После `verified` **`verifier` мержит MR задачи в ветку волны** (или фиксирует `ready to merge`), проверяет сборку/старт в контексте ветки волны и коммитит/подготавливает task-report **после прохождения проверок**. При `ready to merge` назначить исполнителя merge; после фактического merge подтвердить пост-merge проверки и актуализировать/подтвердить отчёт (задача не `done` до этого).
12. При сбое сборки/старта/тестов `verifier` не исправляет код/тесты. Оркестратор инициирует triage `architect` → корректирующие `T-*` в `todo.md` с обоснованием, зафиксированным в corrective задачах и в `wave-*-report.md` (маппинг «причина/затронутые T-* → корректирующая T-*»); разные причины — несколько задач и при необходимости несколько `implementer`, одна причина с пересекающимся ownership — одна задача.

## После волны: wave-проверка и merge ветки волны
13. После влития **всех задач волны** в ветку волны запустить `verifier` (режим wave) для проверок **на ветке волны** по сценарию, описанному `architect` при декомпозиции (конкретный перечень: общие проверки + добавленные/изменённые механики; если их нет — явно «только сборка и запуск», если не указано иное). При необходимости привлечь `scenario-tester`.
14. `verifier` формирует и коммитит `docs/projectDocs/reports/wave-<N>-report.md` после прохождения wave-проверок. При выполнении всех условий `verifier` мержит **ветку волны в основную ветку** (или фиксирует `ready to merge` при отсутствии прав с назначением исполнителя оркестратором); отчёт волны попадает в `main` вместе с веткой волны.
15. При проблемах на волне: анализ `architect` → корректирующие задачи с учётом разбивки причин по задачам волны (разные причины — несколько задач и при необходимости несколько `implementer`) → реализация/проверки на ветке волны → повтор wave-проверок.

## Итог
Оформить: «Следующие запуски…», «Ветки/MR/артефакты…», «Ожидаемые выходы (`.tmp` ввод удалён, отчёты закоммичены `verifier` после проверок, `wave-*-report.md` в ветке волны)», «Критерии перехода (per-task verified→merge в ветку волны→task-report, затем wave-проверки по сценарию→merge ветки волны в main)».

## Ограничения
- Не менять `AGENTS.md` и `docs/gameDocs/rules.md` без отдельного явного запроса.
- Не править `todo.md` кому-либо, кроме `architect` (и только в отдельной ветке по спецзапросу).
- Изменения процесса не имеют обратной силы.
