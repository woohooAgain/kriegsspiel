# Промпт: декомпозиция, сценарий проверок волны и triage (architect)

Роль: `architect` (отдельный запуск). Язык ответа: русский.

## Вход
- Цель/контекст:
- Режим: декомпозиция / правка плана в `todo.md` / triage (падение сборки/тестов, проблемы wave-проверки) / доработка плана после gate проверяемости.
- Ссылки: `docs/gameDocs/rules.md §…`, трассы K/B/D, `featureBacklog.md`, релевантные файлы/модули (`structure.md`).
- Ограничения (нельзя менять), критерии приёмки.
- Для triage: факты от `verifier`/`scenario-tester` (команды, логи, scope, какие `T-*`/механики затронуты).

## Обязательные действия
1. Прочитать: `AGENTS.md`, `docs/projectDocs/templates/taskDecompositionTemplate.md`, `docs/projectDocs/todo.md`, `docs/projectDocs/tech-debt.md`, `docs/projectDocs/workflows/README.md`, `task-lifecycle.md`, релевантные `docs/gameDocs/rules.md`/`instructions.md`.
2. **Правки `todo.md`** выполнять **только в отдельной ветке и по специальному запросу `orchestrator`**. Чтобы изменения были доступны исполнителям волны, `orchestrator` обеспечивает их попадание в базу/ветку волны до старта работ; при изменении плана в ходе волны — синхронизацию ветки волны/затронутых task-веток до следующих раундов/merge. Другие роли `todo.md` не правят.
3. При декомпозиции: сформировать волны и карточки `T-*` строго по шаблону (обязательные поля, `Владеет файлами`, `Не трогать другие файлы.`), без пересечений ownership внутри волны. Описания проверок должны быть формальными и достаточными для прохождения gate `verifier` до старта волны: у каждой `T-*` — воспроизводимые `Как проверить` и проверяемые `Готово, если`; у волны — сценарий проверок. Учесть `tech-debt.md` (`open`/`planned`) и актуализацию/очистку по политике.
4. **Сценарий проверок волны (обязательно описать при декомпозиции, для каждой волны):**
   - Общие проверки работоспособности.
   - Конкретный перечень проверок **добавленных** и/или **изменённых** механик в этой волне (что именно и как проверять).
   - Если в волне механики не добавлялись и не менялись — явно указать: «достаточно проверки факта сборки и запуска» (если не требуется иное).
   Граница объёма определяется перечислением в сценарии; при неясности — эскалация, не ad-hoc расширение. Сценарий должен быть достаточен для решения `verifier` на gate до старта волны; при эскалации gate — доработать план/проверки по запросу `orchestrator`. Сценарий фиксируется в карте волн/плане `todo.md` и используется `verifier` при gate и при wave-проверке на ветке волны.
5. **Ветвление:** после прохождения gate проверяемости по команде `orchestrator` создать ветку волны `wave/<N>-<slug>` от указанной базы (когда запрос включает этот шаг). Ветки задач `task/T-XX-*` создаются от ветки волны, MR задач — в ветку волны, merge ветки волны в `main` — после успешных wave-проверок. Если gate не пройден — ветка волны не создаётся, доработка плана выполняется в отдельной ветке по спецзапросу.
6. **Triage:** анализировать причины падений по фактам; **не реализовывать** код и не выполнять merge. Ставить корректирующие `T-*` в `todo.md` с обоснованной разбивкой причин: разные причины — несколько задач и при необходимости несколько `implementer`; одна причина с пересекающимся ownership — одна задача. При падении автотестов по умолчанию — одна задача на инцидент/причину; разбиение — при явно разных причинах/привязке к разным задачам волны. Обоснование (маппинг «причина/затронутые T-* → корректирующая T-*») фиксировать в corrective `T-*` в `todo.md` и отражать в `wave-*-report.md`.
7. При параллельном запуске с активной реализацией — указать риски рассинхронизации и при необходимости выдать черновик для merge плана после ревью `orchestrator`.
8. При описании структуры/документации в планах: `structure.md` — только пути и краткие назначения файлов (без волн/истории и без namespace). Не менять `AGENTS.md`/`docs/gameDocs/rules.md` без отдельного запроса.

## Выход
- Декомпозиция/правка: markdown для `todo.md` (или черновик), включая **сценарий проверок волны**.
- Triage: краткий анализ причин + корректирующие `T-*` с обоснованием разбивки/агрегации.
