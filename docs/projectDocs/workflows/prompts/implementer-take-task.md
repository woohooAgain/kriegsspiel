# Промпт: взять задачу в работу (implementer)

Роль: `implementer` (один запуск = одна задача `T-XX`). Язык: думать на английском, ответ на русском.

## Вход
- `T-XX` (карточка в `docs/projectDocs/todo.md`)
- Ветка волны (база): `wave/<N>-<slug>`
- Ветка задачи: `task/T-XX-<kebab-slug>` (создать от ветки волны; если существует — работать в ней)
- Целевая ветка MR: ветка волны `wave/<N>-<slug>`
- Раунд: `1` (при `changes requested` — `2`, `3`, …, приложить замечания `verifier`)

## Обязательные действия
1. Прочитать карточку `T-XX`, `AGENTS.md`, `docs/projectDocs/instructions.md`, связанные `docs/gameDocs/rules.md §…`. **Перед началом выполнения проверить наличие формальных способов проверки факта выполнения** для своей части (`Как проверить`, `Готово, если`; при участии в контексте волны — понятность сценария проверок волны). При недостаточности/отсутствии описаний — эскалировать `orchestrator`/`verifier` и не начинать реализацию (статус `blocked`/уточнение) до доработки плана.
2. Работать **только** с файлами из `Владеет файлами`. Не менять: `AGENTS.md`, `docs/gameDocs/rules.md`, `docs/projectDocs/todo.md`, канонические файлы отчётов в `docs/projectDocs/reports/` (кроме временного ввода в `.tmp`, см. ниже).
3. Вести работу **только в ветке задачи**. **Запрещено коммитить в `main`/ветку волны и выполнять merge.** Коммиты в ветку задачи — только если явно разрешено. Файлы `docs/projectDocs/reports/.tmp/*` не коммитить (игнорируются git).
4. Код без комментариев, если явно не просили. Следовать `instructions.md`.
5. **Запустить автотесты/проверки из `Как проверить` в своей ветке** до передачи на верификацию. Зафиксировать команды и результаты. При невозможности прогона — `blocked`/ограничение с доказательствами (не «готово к merge»).
6. Подготовить **структурированный ввод для `verifier`** во временном файле:
   - путь: `docs/projectDocs/reports/.tmp/implementer-T-XX-r<N>.md` (`N` — номер раунда),
   - содержимое: минимум — раунд и закрытые замечания (если есть), ветка/база/MR, что сделано по `Что сделать`, изменённые файлы (только ownership), проверки (команды→результаты, ограничения), статус `готово к verifier`/`blocked`, предложения `TD-*` при наличии, раздел **`Процесс (трение)`** (старт/конец или отметки раундов, неоднозначности со ссылками на карточку/`docs/gameDocs/rules.md §…`/док/файл, лишние поиски и причина: чего не хватило в `structure.md`/ownership/шаблоне/требованиях, оценка доп. затрат `низко/средне/высоко` без метрик контекста, предложения улучшений).
7. Подготовить/обновить **MR задачи в ветку волны** (не в `main`). **Не выполнять merge.**
8. **Перед передачей результатов на проверку удалить** временный файл `.tmp/implementer-T-XX-r<N>.md`. Полное содержимое ввода должно быть передано в ответе/MR (ограничение: после удаления файл недоступен `verifier`, ответственность за полноту на `implementer`). При получении доработок — создать новый файл следующего раунда и снова удалить перед передачей.
9. Находки вне scope — не править молча: предложить `TD-*` или постановку задачи через `orchestrator`/`architect` (самостоятельно `todo.md` не править).

## Выход
Краткое сообщение оркестратору/`verifier`: статус, раунд, ветка, MR, результаты проверок, ключевые фрикции, подтверждение удаления `.tmp` файла текущего раунда.
