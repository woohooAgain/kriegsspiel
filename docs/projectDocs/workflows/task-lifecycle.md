# Жизненный цикл задачи, волны и фичи

Роли: `orchestrator`, `analyst`, `architect`, `implementer`, `verifier`, `scenario-tester`, `process-master`, `rules-auditor`, `docs-maintainer`, `repo-navigator`.

## Операционные принципы
- **Каждая роль выполняет конкретные действия сама** (чтение файлов, анализ, подготовка артефактов). При блокере вне полномочий — эскалация с фактами (`ARTIFACTS`/refs) и остановка в своей зоне.
- **`orchestrator` — дирижёр:** не читает файлы, не анализирует и не синтезирует; передаёт refs/цель/ограничения между ролями и показывает только Status Envelope/короткие статусы.
- **File-first:** детали передаются через артефакты в ветке/репозитории. В коммуникации с оркестратором — только Status Envelope (≤~10 строк) + refs; без полных логов/диффов/копипаста. Доработки — дельта.
- **Обратной силы нет:** правила применяются к новым задачам/волнам/спекам/отчётам; старые артефакты не приводятся задним числом. Анализ должен уметь извлекать информацию из разного представления и явно фиксировать недостающие данные.

## Модель запусков
- Каждая роль — **отдельный запуск** (по умолчанию). Один запуск `implementer` обслуживает **одну** `T-*`.
- **Валидация строго по одной задаче:** проверка, `verified` и merge в ветку волны — отдельно для каждой `T-XX`. Batch запрещён.
- **Итерации:** handoff-артефакт/refs `implementer` → `verifier` → при `changes requested` новый раунд `implementer` в той же ветке задачи до `verified`/`blocked`.
- Параллельные `implementer` в волне допустимы только при отсутствии пересечений `Владеет файлами` (группы определяет `architect` в launch-плане).

## Жизненный цикл фичи (до декомпозиции)
- `backlog` — идея в `docs/gameDocs/featureBacklog.md`.
- `spec_in_progress` / `spec_blocked` — `analyst` готовит/уточняет `FS-*`, фиксирует решения и неоднозначности.
- `ready_for_decomposition` — `FS-*` утверждён/готов (цель, поведение, scope, критерии, нет открытых блокирующих вопросов). Вход для `architect`.
- Неоднозначности правил/требований от `architect`/`implementer` маршрутизируются через `orchestrator` к `analyst`; решение фиксируется в артефакте (`FS-*`/уточнение) со ссылками на `rules.md §…`. Если `analyst` не может разрешить вопрос/противоречие или предполагаются изменения правил — эскалация/консультация с `rules-auditor` (через `orchestrator`) как с финальным источником истины по согласованности и трактовке правил; канон `rules.md` не меняется без отдельного запроса с подтверждением.

## Gate проверяемости (до старта волны)
- `verifier` проверяет достаточность формальных описаний: для каждой `T-*` — `Как проверить` и `Готово, если`; для волны — сценарий проверок (общие + добавленные/изменённые механики или явное «только сборка и запуск»). Launch-план/ownership/refs должны быть достаточны для запуска.
- При недостаточности — `gate_failed`, эскалация `orchestrator` **до начала работ**: ветка волны не создаётся, задачи не запускаются. Доработка `architect` (и при необходимости `analyst` по смыслу фичи) → повторный gate.
- Каждый исполнитель перед стартом своей части проверяет проверяемость своего объёма и при проблемах эскалирует/не стартует.

## Ветвление
- После `gate_passed` по команде `orchestrator` `architect` создаёт **ветку волны** `wave/<N>-<slug>` от указанной базы. Актуальный план/сценарий/launch-план доступен в базе/ветке волны до старта; синхронизация при изменениях — до следующих раундов/merge по решению `orchestrator` (через ответственные роли).
- Ветка задачи: `task/T-XX-<kebab-slug>` от ветки волны; изменения только в `Владеет файлами`.
- MR задач → в **ветку волны**. `implementer` не мержит. `verifier` мержит MR задач и ветку волны в `main` (при правах/условиях); прямые коммиты в `main` запрещены. `verifier` коммитит отчёты `docs/projectDocs/reports/**` после проверок; handoff/код — в ветке задачи по правилам процесса.

## Состояния задачи
- `backlog` / `planned` — определена в плане.
- `ready` — gate пройден, зависимости/ownership/проверки ясны.
- `in_progress` — `implementer` работает в ветке задачи, выполняет проверки.
- `in_review` — handoff + MR/ref готовы, идёт per-task проверка `verifier`.
- `verified` — критерии подтверждены, готово к merge/влито в ветку волны по процессу.
- `done` — влита в ветку волны, пост-merge проверки в контексте ветки волны пройдены, task-report финализирован/закоммичен `verifier` после проверок.
- `blocked` — зависимость/неясность/сбой; причина и refs зафиксированы (в артефакте), при необходимости triage `architect` или уточнение `analyst`.

## Проверки, handoff и triage
- `implementer` запускает проверки из `Как проверить` в своей ветке, фиксирует подробности в handoff-артефакте (file-first) и возвращает Status Envelope + refs. При невозможности — `blocked` с доказательствами.
- `verifier` читает артефакты сам, сверяет ownership/DoD/проверки, не чинит код/тесты. При сбое — факты/refs и эскалация на `architect`.
- **Корректирующие задачи:** `architect` анализирует причины и фиксирует маппинг «причина/затронутые T-* → корректирующая T-*» в `todo.md`/артефакте triage и (через `verifier`/вклад) в `wave-*-report.md`. Разные причины — разные задачи и при необходимости разные implementer; одна причина с пересекающимся ownership — одна задача.
- `scenario-tester` даёт воспроизводимый ввод для wave-проверки/спорных случаев через артефакты и Status Envelope.

## Завершение волны и ретро процесса
- После влития всех задач `verifier` выполняет wave-проверки на ветке волны по сценарию `architect` (с `scenario-tester` при необходимости), формирует/коммитит `wave-*-report.md` и мержит ветку волны в `main` при условиях.
- `process-master` анализирует волну (проблемы, утечки, эффективность мер, циклы/регрессии, баланс детерминизм/сложность), фиксирует `PI-*` в `docs/projectDocs/process-improvement-log.md` и передаёт вклад в `## Ретро процесса`/меры `wave-*-report.md` (канонический коммит отчёта — `verifier`). Может обновлять процессные описания/шаблоны/промпты в рамках полномочий; `AGENTS.md`/`rules.md` — только отдельным запросом.
- При недостатке данных в старых артефактах `process-master` фиксирует пробелы явно (без догадок).

## Матрица ролей (кратко)
| Роль | Делает | Не делает |
|------|--------|-----------|
| `orchestrator` | маршрутизация, запуск агентов, передача refs/статусов, контроль переходов | не читает файлы, не анализирует, не синтезирует, не выводит детали, не правит `todo.md`/код |
| `analyst` | `FS-*`, готовность фич, разрешение неоднозначностей требований в рамках `rules.md`; при противоречиях/неразрешимых вопросах или предполагаемых изменениях правил — эскалация/консультация с `rules-auditor` | не правит `todo.md`/`rules.md`/`AGENTS.md`, не декомпозирует в `T-*`, не мержит |
| `architect` | план/`todo.md` (отдельная ветка по спецзапросу), сценарии, launch-план, triage, корректирующие `T-*`, ветка волны по команде | не реализует код, не мержит, не чинит код/тесты |
| `implementer` | одна `T-*`, ветка задачи, проверки, handoff/MR file-first | не меняет чужие файлы, не правит `todo.md`, не мержит |
| `verifier` | gate, per-task/wave проверки, merge, отчёты после проверок | не чинит код/тесты, не правит `todo.md`, не batch-merge |
| `scenario-tester` | воспроизводимые прогоны, ввод для wave-проверки | не чинит, не мержит, не правит `todo.md` |
| `process-master` | ретро/меры процесса, `PI-*`, контроль эффекта/циклов/сложности | не чинит продукт, не заменяет triage `architect`, не меняет `rules.md`/`AGENTS.md` без запроса |
| `rules-auditor` | аудит `rules.md`, поиск противоречий/пробелов, предложения ребаланса, экспертные заключения (в т.ч. для `analyst`); подготовка изменений правил только по отдельному запросу с подтверждением, в отдельной ветке и через MR | не меняет `rules.md` без запроса+подтверждения, не правит `todo.md`, не реализует продуктовый код |
| `docs-maintainer` | `structure.md` и согласованные docs | не меняет логику без задачи |
| `repo-navigator` | поиск контекста/путей | — |

## Определение «задача закрыта» (минимум)
- `Готово, если` выполнено (или перенесено согласованно со ссылкой).
- Проверки из `Как проверить` выполнены `implementer` и подтверждены `verifier` (evidence/refs доступны).
- MR влита в **ветку волны** после `verified`; пост-merge сборка/старт в контексте ветки волны успешны.
- `task-T-XX-*.md` финализирован и закоммичен `verifier` после проверок.
- Handoff-артефакты/refs оформлены по file-first правилам процесса.
- Структура актуализирована при необходимости; `AGENTS.md`/`rules.md` не менялись без отдельного разрешения.
