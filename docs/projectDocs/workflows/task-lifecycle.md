# Жизненный цикл задачи и волны

Роли: `orchestrator`, `architect`, `implementer`, `verifier`, `scenario-tester`, `rules-auditor`, `docs-maintainer`, `repo-navigator`.

## Модель запусков
- Каждая роль — **отдельный запуск** с соответствующим промптом, не совмещение всех ролей в одном агенте по умолчанию.
- Один запуск `implementer` обслуживает **одну** `T-*` (если оркестратор явно не оговорил иное). Параллельные `implementer` допустимы только при отсутствии пересечений `Владеет файлами`.
- **Валидация строго по одной задаче:** проверка, `verified` и merge в ветку волны — отдельно для каждой `T-XX`. Batch запрещён.
- **Итерации:** ввод `implementer` → `verifier` → при `changes requested` новый раунд `implementer` в той же ветке задачи до `verified`/`blocked`.

## Gate проверяемости (до старта)
- Перед началом работ по волне `verifier` проверяет и решает, достаточны ли формальные описания проверки факта выполнения: для каждой `T-*` волны — `Как проверить` и `Готово, если`; для волны — сценарий проверок волны (общие проверки + проверки добавленных/изменённых механик либо явное «только сборка и запуск», если применимо).
- При недостаточности (в т.ч. отсутствует сценарий/проверки волны или проверки задач) `verifier` эскалирует `orchestrator` **до начала работ по волне**. Ветка волны не создаётся, задачи не запускаются. `orchestrator` отправляет план на доработку `architect` (в отдельной ветке по спецзапросу); после обновления плана gate повторяется.
- `orchestrator` и каждый исполнитель перед началом своей части также проверяют наличие/понятность формальных способов проверки своего объёма и при проблемах эскалируют (не приступая к работам, требующим валидного плана проверок).

## Ветвление волны и задач
- После прохождения gate по команде `orchestrator` `architect` создаёт **ветку волны** `wave/<N>-<slug>` от базы, указанной оркестратором (обычно `main`). `todo.md` правится в отдельной ветке по спецзапросу; `orchestrator` обеспечивает доступность актуального плана/сценария волны в базе или ветке волны до старта работ. При изменении плана в ходе волны ветка волны и затронутые task-ветки синхронизируются до следующих раундов/merge по решению `orchestrator`.
- Ветка задачи: `task/T-XX-<kebab-slug>` создаётся **от ветки волны**. Все изменения задачи — только в этой ветке и в пределах `Владеет файлами`.
- MR задачи нацеливается в **ветку волны**. `implementer` делает коммиты только в ветке задачи (если явно разрешено) и не выполняет merge. `verifier` выполняет merge MR задач в ветку волны и merge ветки волны в `main` (допустимое исключение: коммиты файлов отчётов в `docs/projectDocs/reports/` в ветке волны после проверок). Прямые коммиты в `main` запрещены.
- После `verified` **`verifier` выполняет merge MR задачи в ветку волны** и проверяет сборку/старт в контексте ветки волны. При отсутствии технических прав `verifier` фиксирует `ready to merge` с причиной и коммитит/подготавливает task-report после проверок; `orchestrator` назначает исполнителя merge, после фактического merge подтверждаются пост-merge проверки и `verifier` актуализирует/подтверждает финальное состояние отчёта (задача не `done` до этого).
- После успешной верификации всех задач и wave-проверок ветка волны мержится в `main` (`verifier` или назначенный исполнитель при отсутствии прав, с подтверждёнными условиями). Запрещено «чинить» `main` напрямую.

## Состояния задачи (рекомендуемые)
- `backlog` — идея/запрос.
- `ready` — карточка `T-*` готова (ownership, зависимости, проверки, DoD, волна).
- `in_progress` — `implementer` работает в ветке задачи, выполняет проверки из `Как проверить`.
- `in_review` — MR в ветку волны готов, идёт per-task проверка `verifier`.
- `verified` — критерии задачи подтверждены, MR готов/влит в ветку волны по процессу.
- `done` — задача влита в ветку волны, пост-merge проверки в контексте ветки волны пройдены, task-report закоммичен `verifier` после проверок.
- `blocked` — зависимость/неясность/сбой; причина зафиксирована, при необходимости triage `architect`.

## Проверки, отчёты и triage
- `implementer` запускает автотесты/проверки из `Как проверить` **в своей ветке** до передачи на верификацию. При невозможности — `blocked`/ограничение с доказательствами.
- `implementer` готовит ввод во временном файле `docs/projectDocs/reports/.tmp/implementer-T-XX-r<N>.md` и удаляет его **перед передачей результатов на проверку**; при доработке — новый файл следующего раунда с удалением перед передачей. `.tmp/*` (кроме `README.md`) не коммитится (игнорируется git); полнота переданного ввода в ответе/MR — ответственность `implementer`.
- `verifier` финализирует и коммитит `task-T-XX-*.md` в ветке волны **после прохождения проверок**. `verifier` может коммитить только `docs/projectDocs/reports/**` в ветке волны; при отсутствии прав — передаёт финальное содержимое, коммит выполняет назначенный оркестратором исполнитель. При `ready to merge` отчёт актуализируется после фактического merge/подтверждения пост-merge.
- При сбое сборки/тестов (post-merge в ветке волны или wave-проверка) `verifier` **не исправляет** код/тесты: фиксирует факты и эскалирует на `architect`.
- **Корректирующие задачи:** `architect` анализирует причины и разбивку по задачам волны. Обоснование фиксируется в corrective `T-*` в `todo.md` и в `wave-*-report.md` (маппинг «причина/затронутые T-* → корректирующая T-*»). Разные причины — несколько задач и при необходимости несколько `implementer`; одна причина с пересекающимся ownership — одна задача. При падении автотестов по умолчанию — одна задача на инцидент/причину; разбиение — при явно разных причинах/привязке к разным задачам волны.

## Сценарий проверок волны и завершение волны
- **Сценарий проверок волны** описывает `architect` при декомпозиции (обязательно в карте волн/плане): общие проверки работоспособности + конкретные проверки **добавленных/изменённых** механик. Если механики не добавлялись и не менялись — явно «достаточно проверки факта сборки и запуска» (если не указано иное). `verifier` следует сценарию; при неясности — эскалация.
- После влития всех задач волны `verifier` выполняет wave-проверки **на ветке волны** по сценарию `architect` (с привлечением `scenario-tester` при необходимости), формирует и коммитит `wave-*-report.md`.
- При проблемах на волне: анализ `architect` → корректирующие `T-*` с обоснованной разбивкой причин (разные причины — несколько задач/при необходимости несколько `implementer`) → реализация/проверки на ветке волны → повтор wave-проверок.
- При выполнении всех условий `verifier` мержит ветку волны в `main`. Wave-report попадает в `main` вместе с веткой волны.

## Матрица ролей
| Роль | Типично делает | Не делает |
|------|----------------|-----------|
| `orchestrator` | координация волны, gate проверяемости/запрос доработок плана, запуск ролей, проверка ownership/зависимостей, решения по эскалациям | не правит `todo.md` (кроме запроса `architect`), не реализует/не мержит как исполнитель по умолчанию |
| `architect` | декомпозиция и правки `todo.md` в отдельной ветке по спецзапросу, создание ветки волны по команде `orchestrator`, сценарии проверок волн, triage падений и корректирующие `T-*` с обоснованной разбивкой причин | не реализует код, не выполняет merge, не чинит код/тесты напрямую |
| `implementer` | проверка наличия/понятности проверок своей задачи перед стартом (эскалация при проблемах), реализация одной `T-*` в ветке от ветки волны, проверки в ветке, временный ввод в `.tmp` (с удалением перед передачей), MR в ветку волны | не меняет чужие файлы, не правит `todo.md`, не мержит, не финализирует/не коммитит отчёты в `reports/` |
| `verifier` | gate проверяемости до старта волны (решение о достаточности описаний), per-task верификация, merge задач в ветку волны, финализация/коммит отчётов в ветке волны после проверок, wave-проверки по сценарию `architect`, merge ветки волны в `main` (или `ready to merge` с эскалацией/актуализацией отчёта) | не исправляет код/тесты, не правит `todo.md`, не делает batch-merge |
| `scenario-tester` | воспроизводимые прогоны, smoke/сценарии для wave-проверки, ввод для отчёта | не чинит код, не мержит, не правит `todo.md` |
| `rules-auditor` | сверка с `docs/gameDocs/rules.md` | не меняет `rules.md` |
| `docs-maintainer` | актуализация `structure.md` и согласованных docs | не меняет логику без задачи |
| `repo-navigator` | поиск контекста/путей | — |

## Определение «задача закрыта» (минимум)
- Все пункты `Готово, если` выполнены или перенесены в согласованный `TD-*`/новую карточку со ссылкой.
- Проверки из `Как проверить` выполнены `implementer` в ветке (или ограничение зафиксировано и принято) и подтверждены `verifier`.
- MR задачи влит в **ветку волны** после `verified`; пост-merge сборка/старт в контексте ветки волны успешны.
- `task-T-XX-*.md` финализирован и закоммичен `verifier` после проверок.
- Временный `.tmp`-ввод `implementer` удалён перед передачей на проверку.
- Нет незадокументированных изменений структуры без обновления `structure.md` при необходимости.
- `AGENTS.md` и `docs/gameDocs/rules.md` не менялись без отдельного разрешения.

## Изменения процесса
Изменения процесса не имеют обратной силы: новые правила применяются к новым задачам, волнам и отчётам; существующие артефакты не приводятся задним числом к обновлённому виду.
