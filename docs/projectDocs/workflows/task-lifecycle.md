# Жизненный цикл задачи

Неспецифичные роли (подставлять в промпты): `orchestrator`, `planner`, `implementer`, `verifier`, `scenario-tester`, `rules-auditor`, `docs-maintainer`, `repo-navigator`.

## Модель запусков (важно)
- Каждая роль ниже — это **тип запуска** агента/сабагента с соответствующим промптом, а не «один агент играет все роли» по умолчанию.
- **Один запуск `implementer`** обслуживает **одну** карточку `T-*` (если оркестратор явно не оговорил иное). Параллельные запуски `implementer` допустимы только при отсутствии пересечений `Владеет файлами` внутри волны.
- **Итерации цикла качества**: отчёт `implementer` → запуск `verifier` → при `changes requested` новый запуск `implementer` с приложенным списком замечаний (раунд N+1). Повторять до `verified` или `blocked`.

## Состояния (рекомендуемые)
- `backlog` — идея/запрос в `docs/gameDocs/featureBacklog.md` или свободная формулировка.
- `ready` — есть декомпозиция: карточка `T-*` с `Владеет файлами`, `Зависимости`, `Как проверить`, `Готово, если`, волна определена.
- `in_progress` — запущен(ы) `implementer` в ветках задач; идёт разработка в границах ownership.
- `in_review` — для задачи подготовлен MR/набросок готовности и идёт проверка (`verifier` и/или `scenario-tester`).
- `verified` — **Завершено по критериям задачи**: `Готово, если` выполнены, проверки/тесты по карточке пройдены; MR готов к вливанию ответственным по процессу.
- `done` — изменения влиты в основную ветку по правилам ниже, пост-merge проверки пройдены (для задачи или в составе волны), при необходимости обновлены docs/долг.
- `blocked` — внешняя зависимость/неясность правил; зафиксировано в карточке и/или `tech-debt.md`.

## Git и ветки (обязательно)
- **Запрещено коммитить в `main`** и запрещено выполнять merge в `main`/целевую ветку любым агентом, кроме явного отдельного запроса пользователя вне цикла задачи. Рабочие коммиты — **только в ветке задачи** `task/T-XX-<kebab-slug>`, созданной от базы, указанной оркестратором.
- Все изменения по задаче — только в этой ветке и только в пределах `Владеет файлами`.
- По готовности к проверке `implementer` оформляет **MR/PR** в целевую ветку (указанную оркестратором) и не выполняет merge сам.
- **`verifier` всегда выполняет merge MR в целевую ветку после статуса `verified`** (DoD, проверки карточки, требуемые тесты/прогоны). Если merge невозможен технически — `verifier` ставит `ready to merge` в отчёте с причиной и ссылкой на MR; оркестратор назначает исполнителя merge, **готовность определяется `verifier`**.
- После каждого merge в целевую ветку **обязательно** проверка: проект **собирается и стартует** (команды из `instructions.md`/карточки и запуск по репозиторию). При сбое — `blocked` или новый раунд по решению оркестратора.
- **После выполнения всех задач волны** — полноценное тестирование **запуск и игра** (`scenario-tester`/оркестратор). Итоги — отчёт волны в `docs/projectDocs/reports/wave-*-report.md`; дефекты — новые `T-*` или `TD-*`.

## Отчёты (обязательно)
- Отчёты хранятся в `docs/projectDocs/reports/` (см. `reports/README.md`): по задачам `task-T-XX-...md`, по волнам `wave-<N>-report.md`.

## Матрица ролей (кратко)
| Роль | Форма запуска (типично) | Типично делает | Не делает |
|------|-------------------------|---------------|-----------|
| `orchestrator` | один координатор на поток работы | волны, параллельные запуски `implementer`, сбор отчётов, запуск `verifier`/`scenario-tester`, решения о merge и о wave-level тестировании | не правит код/правила “за всех” без роли исполнителя |
| `planner` | отдельный запуск при декомпозиции | `T-*` по шаблону, учёт `tech-debt.md` и `docs/gameDocs/rules.md` | не реализует код приложения |
| `implementer` | отдельный запуск на `T-*` (и раунд) | ветка задачи, правки только в ownership, проверки по карточке, подготовка MR, отчёт | не меняет чужие файлы, не мержит в main без разрешения, не меняет `AGENTS.md`/`rules.md` без запроса |
| `verifier` | отдельный запуск на задачу/пакет | проверка diff/MR и артефактов, вердикт verified/changes requested/blocked, **всегда выполняет merge в целевую ветку после verified** (или фиксирует `ready to merge` при отсутствии прав), пост-merge сборка+старт | не внедряет большие фичи вместо `implementer` |
| `scenario-tester` | отдельные запуски по сценариям/волне | интеграционные прогоны, «запуск и игра», отчёты и `TD-*` | не подменяет обязательные проверки карточки; не мержит |
| `rules-auditor` | отдельный запуск по запросу | сверка с `rules.md`, вопросы/противоречия | не меняет `rules.md` |
| `docs-maintainer` | отдельный запуск после изменений структуры | `structure.md` и согласованные карты docs | не меняет логику без задачи |
| `repo-navigator` | отдельный запуск по запросу | поиск контекста, карты путей | — |

## Переходы и артефакты
- `backlog` → `ready`: карточка `T-*` по шаблону; учтён `tech-debt.md`. При параллельном планировании и активной реализации — следовать `README.md` (риски конфликтов).
- `ready` → `in_progress`: оркестратор запускает `implementer`(ов) для задач волны без пересечений ownership; каждый работает в своей ветке. Артефакт — идентификаторы веток/запусков.
- `in_progress` → `in_review`: отчёт `implementer` (файлы в ownership, команды, ограничения окружения, раунд, ссылка/статус MR). Оркестратор запускает `verifier`.
- `in_review` → `verified`: вердикт `verifier` + чеклист `Готово, если`. Замечания → новый запуск `implementer` (итерация) с пакетом замечаний.
- `verified` → `done` (для задачи): `verifier` выполняет merge MR в целевую ветку → пост-merge проверка **сборка и старт** → при успехе задача `done`; при провале — `blocked` или доработка (новый раунд) по решению оркестратора. Фиксируется в отчёте задачи (`docs/projectDocs/reports/`).
- После всех задач волны → этап **wave-level integration testing: запуск и игра** (`scenario-tester`/оркестратор), отчёт `docs/projectDocs/reports/wave-*-report.md`; найденные проблемы → новые `T-*`/`TD-*` или хотфиксы по процессу.
- любой → `blocked`: причина, вопросы, запись в карточке и при необходимости `TD-*`.

## Определение “задача может быть закрыта” (минимум)
- Все пункты `Готово, если` выполнены или перенесены в согласованный `TD-*`/новую карточку со ссылкой.
- Проверки из `Как проверить` выполнены (или причина пропуска зафиксирована и принята).
- MR влит в основную ветку после `verified`, пост-merge: **сборка успешна и приложение запускается** по инструкции репозитория.
- Нет незадокументированных изменений структуры без обновления `structure.md`, если требовалось.
- `AGENTS.md` и `docs/gameDocs/rules.md` не менялись без отдельного разрешения.
