# Шаблон декомпозиции задач (backlog/feature spec → параллельно исполняемые задачи)

Назначение: описывает **форму и правила** декомпозиции в список задач, которые можно отдавать `implementer` **без дополнительной декомпозиции** и выполнять **параллельно** в рамках одной волны (при соблюдении ownership).

Источник стиля: `docs/projectDocs/todo.md`. Общие правила: `AGENTS.md`, `docs/projectDocs/instructions.md`.

> `docs/gameDocs/rules.md` и `AGENTS.md` не менять без отдельного явного запроса. Изменения процесса не имеют обратной силы.

---

## 1) Входные данные для декомпозиции

Укажи явно (refs):
- **Цель/контекст**: что нужно довести (запрос/issue/notes).
- **Вход от `analyst` (для новых фич):** утверждённая спека `docs/gameDocs/featureSpecs/FS-*.md` со статусом `ready_for_decomposition` и/или зафиксированные решения по неоднозначностям. Если не применимо — `N/A` с причиной.
- **Источник правил/требований**: ссылки на `docs/gameDocs/rules.md` (`§…`), предметные трассы (`K/B/D`) при необходимости, `FS-*`, backlog.
- **Текущая база кода**: релевантные проекты/файлы/папки (refs), чтобы корректно назначить ownership.
- **Ограничения**: что нельзя менять, политика коммитов/веток, среда.
- **Критерии приёмки уровня эпика/волны**.
- **Техдолг**: учтённые `TD-*` (`open`/`planned`) из `docs/projectDocs/tech-debt.md` и причины, если не включены.

---

## 2) Правила декомпозиции (обязательно)

### 2.1 File ownership (строго)
- Каждая задача имеет `Владеет файлами` — список путей/паттернов, которые **только эта** задача может менять (включая `(новый)`).
- Исполнитель **не трогает** файлы вне списка. Нужна правка чужого файла — зависимость/отдельная интеграционная задача/волна.

### 2.2 Независимость внутри волны
- Внутри волны задачи **не пересекаются по файлам** и исполняемы **параллельно** в группах, определённых launch-планом.

### 2.3 Волны, зависимости, launch-план
- Задачи сгруппированы по волнам (`Wave 0`, `Wave 1`, ...), у каждой — `Зависимости`.
- Для каждой волны подготовить **launch-план для оркестратора** (как часть плана, машиночитаемо/таблицей): параллельные группы `T-*` без пересечений ownership, порядок запуска/merge-зависимости, refs на сценарий/gate-критерии. Оркестратор использует только статусы/refs, не синтезирует ownership сам.

### 2.4 Процесс, проверки и file-first валидация
- **Gate проверяемости (до старта):** у каждой `T-*` — воспроизводимые `Как проверить` и проверяемые `Готово, если`; у волны — достаточный сценарий проверок. `verifier` решает достаточность; при недостаточности — эскалация, ветка волны не создаётся, задачи не запускаются.
- **Валидация строго по одной задаче (`T-XX`) до merge её MR**; batch запрещён. Доработки — в ветке той же задачи.
- **`implementer`** запускает проверки из `Как проверить` в своей ветке до передачи, сохраняет evidence/handoff file-first (напр. `docs/projectDocs/reports/handoffs/implementer-T-XX-r<N>.md`) и возвращает Status Envelope + refs (без полных логов). При невозможности — `blocked` с доказательствами.
- **`verifier`** проводит per-task/wave проверки, мержит после `verified` (или `ready to merge`), коммитит канонические отчёты после проверок. При сбоях не чинит код/тесты — эскалация на triage `architect`.
- **Корректирующие задачи:** `architect` фиксирует маппинг «причина/затронутые T-* → корректирующая T-*» с обоснованной разбивкой (разные причины — разные задачи/при необходимости разные implementer; одна причина с пересекающимся ownership — одна задача).
- Канонические команды (если применимо): `dotnet build Kriegsspiel.slnx`, `dotnet test Kriegsspiel.Core.Tests/Kriegsspiel.Core.Tests.csproj`, при отдельных test-проектах — `dotnet test Kriegsspiel.slnx`. Отсутствие среды — фиксировать как ограничение с доказательствами.

### 2.5 Трассировка требований
- В `Покрывает` указывать `§...`, `FS-*`, трассы `K/B/D` где уместно. Не придумывать несуществующие ID.

### 2.6 Ограничения
- Код без комментариев, если явно не просили.
- Не менять `AGENTS.md`, `docs/gameDocs/rules.md` без отдельного запроса. `implementer` не правит `todo.md`.
- Детали передаются через артефакты/refs; оркестратору — только статусы.

## 3) Формат выходного документа

```md
# TODO / Backlog decomposition: <краткое название>

Источник требований: <FS-*, rules §…, backlog, запросы>
Учтённый техдолг (`docs/projectDocs/tech-debt.md`): <TD-* или «нет релевантных» + причины>

## Формат и правила работы
(кратко, с учётом file-first, gate, ownership, launch-плана, ролей)

## Карта волн
| Волна | Задачи | Зависимости | Параллельные группы (launch-план) | Сценарий проверок волны (gate) | Заметки |
|---|---|---|---|---|---|

## Карточки задач
...
```

### Карточка задачи
```md
### T-XX — <краткое имя>
- **ID:** `T-XX`
- **Волна:** Wave N
- **Покрывает:** <FS-* / §... / K/B/D>
- **Владеет файлами:**
  - `путь/к/файлу`
  - `путь/к/новому` (новый)
  - Не трогать другие файлы.
- **Зависимости:** <нет | T-* | Wave N>
- **Что сделать:**
  1. ...
- **Как проверить:**
  - `<команда/шаг>`
  - Утверждения: <ожидаемое поведение>
- **Готово, если:**
  - [ ] ...
```

#### Требования к полям
- `ID` стабилен и уникален. `Покрывает` трассируем к `FS-*`/`§…`.
- `Владеет файлами` — явные пути, `(новый)` при создании, строка `Не трогать другие файлы.` обязательна.
- `Как проверить` — воспроизводимые команды/шаги и утверждения (достаточно для gate и верификации).
- `Готово, если` — 3–8 проверяемых пунктов.

---

## 4) Рекомендации
- Разбивай по архитектурным границам; интеграцию чужих файлов выноси в отдельные волны/задачи.
- Для новых типов/контрактов указывай целевое расположение в ownership.
- Избегай расплывчатых формулировок; критерии должны быть проверяемы по артефактам/командам.
