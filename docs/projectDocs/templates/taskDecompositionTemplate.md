# Шаблон декомпозиции задач для ведения разработки (backlog → параллельно исполняемые задачи)

Назначение: этот файл описывает **форму и правила** декомпозиции беклога в список задач, которые можно отдавать агенту-разработчику **без дополнительной декомпозиции** и выполнять **параллельно** в рамках одной волны.

Источник вдохновения по стилю: `docs/projectDocs/todo.md` (разделы «Формат и правила работы», «Карта волн», карточки задач `T-*`).

> Правило: сам файл правил игры (`./rules.md` / `docs/gameDocs/rules.md`) не менять. Общее руководство — `docs/projectDocs/instructions.md`.

---

## 1) Входные данные для декомпозиции (что должен получить агент-декомпозитор)

Укажи явно:
- **Цель/контекст**: что нужно довести/внедрить (ссылка на запрос пользователя, issue/notes).
- **Источник правил/требований**: ссылки на `rules.md`, разделы/пункты (например `§3`, `§6`) или предметные трассы (`K/B/D`), если применимо.
- **Текущая база кода**: ключевые проекты/файлы/папки (по рабочему дереву), чтобы корректно назначить владение файлами.
- **Ограничения**: что нельзя менять (например `AGENTS.md`, файлы правил, конкретные модули), язык текста (русский для описаний задач), политика коммитов и т.д.
- **Критерии приёмки уровня эпика**: что значит «готово» для всей работы (build/test/сценарии/ручные проверки).

## 2) Правила декомпозиции (обязательно к соблюдению)

### 2.1 File ownership (строго)
- Каждая задача имеет `Владеет файлами` — список путей/паттернов, которые **только эта** задача может менять (включая пометки `(новый)`).
- Агент **не трогает** файлы вне своего списка (включая тесты/контракты/конфиги «соседних» задач).
- Если для компиляции/интеграции нужен чужой файл — эта зависимость оформляется через **волны** (см. 2.3): интеграция в чужие файлы делается отдельной задачей/волной-владельцем.

### 2.2 Независимость внутри волны
- Внутри одной волны задачи **не пересекаются по файлам** (нет общего владельца одного и того же пути, кроме осознанно разрешённых read-only зависимостей — но лучше избегать).
- Задачи внутри волны должны быть исполняемы **параллельно**.

### 2.3 Волны и зависимости
- Все задачи сгруппированы по **волнам** (`Wave 0`, `Wave 1`, ...).
- У каждой задачи есть `Зависимости`: какие задачи/волны должны быть завершены перед стартом.
- Новая волна стартует **после** завершения предыдущей и прохождения интеграционных проверок (если они указаны).

### 2.4 Проверки (канонические команды)
Для .NET-репозитория указывай канонические команды (если применимо), например:
- `dotnet build Kriegsspiel.slnx`
- `dotnet test Kriegsspiel.Core.Tests/Kriegsspiel.Core.Tests.csproj`
- `dotnet test Kriegsspiel.slnx` (если есть отдельные test-проекты в solution)

Если в окружении команд нет — явно отмечать: «канонические команды обязательны для фиксации в `Как проверить`».

### 2.5 Трассировка требований
- В поле `Покрывает` указывать ссылки на правила/разделы (например `§2–§5`, `§12`) и предметные трассы (`K/B/D`) где уместно.
- Не придумывать несуществующие ID правок, если их нет в источнике; использовать разделы/механики.

### 2.6 Ограничения по стилю и процессу
- Код без комментариев, **если пользователь явно не попросил**.
- Не менять запрещённые файлы (например `AGENTS.md`, `rules.md`) без отдельного запроса.
- Коммиты/ветки — только по явной просьбе пользователя (если это не оговорено иначе в задаче).

## 3) Формат выходного документа (что нужно сгенерировать)

Результат должен быть в одном markdown-файле со следующей структурой.

### 3.1 Заголовок и мета
```md
# TODO / Backlog decomposition: <краткое название>

Источник требований: <ссылки на rules.md, docs, issue и т.п.>

## Формат и правила работы
(кратко скопировать/адаптировать пункты из раздела 2 этого шаблона)
```

### 3.2 Карта волн (обязательная таблица)
Таблица вида:

| Волна | Задачи | Зависимости | Правило/заметки |
|---|---|---|---|
| Wave 0 — фундамент | `T-01`, `T-02` | нет | Параллельно, файлы не пересекаются. ... |

### 3.3 Карточки задач (для каждой задачи)

Каждая задача — отдельный подраздел и **строго** в формате ниже:

```md
### T-XX — <краткое имя задачи>
- **ID:** `T-XX`
- **Волна:** Wave N
- **Покрывает:** <§... , K/B/D если нужно>
- **Владеет файлами:**
  - `путь/к/файлу.cs`
  - `путь/к/новому_файлу.cs` (новый)
  - Не трогать другие файлы.
- **Зависимости:** <нет | T-01, T-02 | Wave 0>
- **Что сделать:**
  1. ...
  2. ...
  (конкретно, проверяемо; без расплывчатых формулировок вроде “улучшить код”)
- **Как проверить:**
  - `<команда 1>`
  - `<команда 2>`
  - Утверждения: <что должно быть истинно; примеры кейсов/инвариантов>
- **Готово, если:**
  - [ ] ...
  - [ ] ...
```

#### Требования к полям карточки
- `ID`: стабильный идентификатор (`T-01`, `T-10`, …), уникальный в документе.
- `Покрывает`: перечислить разделы правил/механики, которые закрывает задача (и трассы `K/B/D` при необходимости).
- `Владеет файлами`: **явный список** путей. Если создаются файлы — пометить `(новый)`. В конце всегда строка: `Не трогать другие файлы.`
- `Зависимости`: либо `нет`, либо список `T-*`/волн. Не оставлять пустым.
- `Что сделать`: нумерованный список шагов; по возможности ссылайся на контракты/типы/файлы, которые уже есть или будут созданы в указанных зависимостях.
- `Как проверить`: команды + **утверждения/ожидаемое поведение** (что именно проверить: инварианты, кейсы, отсутствие регрессий).
- `Готово, если`: чеклист из 3–8 пунктов, проверяемых без дополнительных уточнений.

## 4) Рекомендации по качеству декомпозиции (чтобы агенту не нужно было додумывать)

- Разбивай по **архитектурным границам**: домен/контракты → механики → интеграция → CLI/UI → уборка/документация (как в `todo.md`).
- Если задача требует изменений «в нескольких местах», почти всегда нужна **предыдущая волна** с новыми контрактами/типами и отдельная волна интеграции.
- Для каждого нового типа/контракта указывай **имя файла и namespace/папку** (если это важно для владельца).
- Избегай задач, где `Что сделать` начинается с “по необходимости…” без критериев — лучше выделить отдельную задачу с явными файлами.
