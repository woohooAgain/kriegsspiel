# Шаблон декомпозиции задач (backlog → параллельно исполняемые задачи)

Назначение: этот файл описывает **форму и правила** декомпозиции беклога в список задач, которые можно отдавать агенту-разработчику **без дополнительной декомпозиции** и выполнять **параллельно** в рамках одной волны.

Источник стиля: `docs/projectDocs/todo.md`. Общее руководство — `docs/projectDocs/instructions.md`.

> Правило: `docs/gameDocs/rules.md` не менять. `AGENTS.md` — только по отдельному явному запросу.

---

## 1) Входные данные для декомпозиции

Укажи явно:
- **Цель/контекст**: что нужно довести/внедрить (ссылка на запрос, issue/notes).
- **Источник правил/требований**: ссылки на `docs/gameDocs/rules.md`, разделы/пункты (например `§3`, `§6`) или предметные трассы (`K/B/D`), если применимо.
- **Текущая база кода**: ключевые проекты/файлы/папки (по рабочему дереву), чтобы корректно назначить владение файлами.
- **Ограничения**: что нельзя менять (например `AGENTS.md`, файлы правил, конкретные модули), язык текста, политика коммитов и т.д.
- **Критерии приёмки уровня эпика**: что значит «готово» для всей работы (build/test/сценарии/ручные проверки).
- **Техдолг**: прочитать `docs/projectDocs/tech-debt.md` до составления волн; перечислить учтённые `TD-*` (`open`/`planned`) и причины, если что-то сознательно не включено. Учесть политику актуализации/очистки активного списка при планировании закрытия `TD-*`.

## 2) Правила декомпозиции (обязательно к соблюдению)

### 2.1 File ownership (строго)
- Каждая задача имеет `Владеет файлами` — список путей/паттернов, которые **только эта** задача может менять (включая пометки `(новый)`).
- Исполнитель **не трогает** файлы вне своего списка (включая тесты/контракты/конфиги «соседних» задач).
- Если для компиляции/интеграции нужен чужой файл — эта зависимость оформляется через **волны**: интеграция в чужие файлы делается отдельной задачей/волной-владельцем.

### 2.2 Независимость внутри волны
- Внутри одной волны задачи **не пересекаются по файлам**.
- Задачи внутри волны должны быть исполняемы **параллельно**.

### 2.3 Волны и зависимости
- Все задачи сгруппированы по **волнам** (`Wave 0`, `Wave 1`, ...).
- У каждой задачи есть `Зависимости`: какие задачи/волны должны быть завершены перед стартом.
- Новая волна стартует **после** завершения предыдущей и прохождения интеграционных проверок (если они указаны).

### 2.4 Процесс, проверки и валидация
- **Gate проверяемости (до старта волны):** у каждой `T-*` должны быть формальные, воспроизводимые `Как проверить` и проверяемые `Готово, если`; для каждой волны — достаточный сценарий проверок волны. До начала работ по волне `verifier` решает, хватает ли описаний; при недостаточности — эскалация `orchestrator`, доработка `architect`, ветка волны не создаётся и задачи не запускаются.
- **Валидация строго по одной задаче (`T-XX`) до merge её MR**; batch-валидация/merge пачкой запрещены. Доработки — только в ветке той же задачи до влития.
- **`implementer` запускает автотесты/проверки из `Как проверить` в своей ветке** до передачи на верификацию; при невозможности прогона фиксируется `blocked`/ограничение с доказательствами.
- **`verifier`** выполняет per-task верификацию, merge после `verified` (или `ready to merge` при отсутствии прав), пост-merge проверку сборки/старта и финализирует отчёт задачи в `docs/projectDocs/reports/`.
- При падении сборки/тестов после merge в ветку волны или на wave-проверке исправления не выполняет `verifier`: проводится triage `architect` и постановка корректирующих `T-*` с обоснованной разбивкой причин по задачам волны (разные причины — несколько задач и при необходимости несколько `implementer`; одна причина с пересекающимся ownership — одна задача).
- Канонические команды (если применимо): `dotnet build Kriegsspiel.slnx`, `dotnet test Kriegsspiel.Core.Tests/Kriegsspiel.Core.Tests.csproj`, при наличии отдельных test-проектов — `dotnet test Kriegsspiel.slnx`. Если в окружении команд нет — явно отмечать в `Как проверить`.

### 2.5 Трассировка требований
- В поле `Покрывает` указывать ссылки на правила/разделы (например `§2–§5`, `§12`) и предметные трассы (`K/B/D`) где уместно.
- Не придумывать несуществующие ID правок, если их нет в источнике.

### 2.6 Ограничения по стилю и процессу
- Код без комментариев, **если пользователь явно не попросил**.
- Не менять запрещённые файлы (`AGENTS.md`, `docs/gameDocs/rules.md`) без отдельного запроса.
- **`implementer` не правит `todo.md` и не финализирует канонические отчёты**; план/карточки меняет только `architect` по запросу `orchestrator` (в отдельной ветке по спецзапросу). Изменения плана должны попасть в базу/ветку волны до старта работ. Временный ввод для `verifier` — `docs/projectDocs/reports/.tmp/implementer-T-XX-r<N>.md` (не коммитить, удалить перед передачей). Коммиты/ветки — по правилам workflows.

## 3) Формат выходного документа

Результат должен быть в одном markdown-файле со следующей структурой.

### 3.1 Заголовок и мета
```md
# TODO / Backlog decomposition: <краткое название>

Источник требований: <ссылки на `docs/gameDocs/rules.md`, docs, issue и т.п.>

Учтённый техдолг (`docs/projectDocs/tech-debt.md`): <список TD-* или «нет релевантных» + примечания>

## Формат и правила работы
(кратко адаптировать пункты из раздела 2 этого шаблона)
```

### 3.2 Карта волн (обязательная таблица)
| Волна | Задачи | Зависимости | Правило/заметки |
|---|---|---|---|
| Wave 0 — фундамент | `T-01`, `T-02` | нет | Параллельно, файлы не пересекаются. **Сценарий проверок волны (достаточный для gate):** общие проверки + конкретный перечень добавленных/изменённых механик (или явно «только сборка и запуск»). |

### 3.3 Карточки задач

```md
### T-XX — <краткое имя задачи>
- **ID:** `T-XX`
- **Волна:** Wave N
- **Покрывает:** <§... , K/B/D если нужно>
- **Владеет файлами:**
  - `путь/к/файлу`
  - `путь/к/новому_файлу` (новый)
  - Не трогать другие файлы.
- **Зависимости:** <нет | T-01, T-02 | Wave 0>
- **Что сделать:**
  1. ...
  2. ...
- **Как проверить:**
  - `<команда 1>`
  - `<команда 2>`
  - Утверждения: <что должно быть истинно; кейсы/инварианты>
- **Готово, если:**
  - [ ] ...
  - [ ] ...
```

#### Требования к полям карточки
- `ID`: стабильный идентификатор (`T-01`, `T-10`, …), уникальный в документе.
- `Покрывает`: разделы правил/механики и трассы `K/B/D` при необходимости.
- `Владеет файлами`: **явный список** путей. Если создаются файлы — пометить `(новый)`. В конце всегда строка: `Не трогать другие файлы.`
- `Зависимости`: либо `нет`, либо список `T-*`/волн.
- `Что сделать`: нумерованный, конкретный и проверяемый список шагов.
- `Как проверить`: команды + **утверждения/ожидаемое поведение**.
- `Готово, если`: чеклист из 3–8 пунктов, проверяемых без дополнительных уточнений.

## 4) Рекомендации по качеству декомпозиции
- Разбивай по **архитектурным границам**: домен/контракты → механики → интеграция → CLI/UI → уборка/документация.
- Если задача требует изменений «в нескольких местах», почти всегда нужна **предыдущая волна** с новыми контрактами/типами и отдельная волна интеграции.
- Для каждого нового типа/контракта указывай имя файла и расположение, если это важно для владельца.
- Избегай расплывчатых формулировок без критериев.
