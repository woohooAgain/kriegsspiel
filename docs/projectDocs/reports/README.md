# Отчёты (reports)

Каталог для структурированных отчётов выполнения задач и волн.

## Что хранить
- **Отчёты по задачам:** `task-T-XX-<short-slug>.md`.
- **Отчёты по волнам:** `wave-<N>-report.md`.
- **Временный ввод implementer:** `docs/projectDocs/reports/.tmp/implementer-T-XX-r<N>.md` (`N` — раунд). Служебные файлы; `implementer` удаляет файл перед передачей результатов на проверку (при доработке создаёт файл следующего раунда и также удаляет перед передачей). Содержимое `.tmp/*` (кроме `README.md`) игнорируется git и не коммитится.

## Ownership и моменты фиксации
- **Канонический владелец отчётов — `verifier`.** `verifier` финализирует и **коммитит отчёты после прохождения проверок**.
  - `task-T-XX-*.md` — после per-task верификации/проверок в контексте ветки волны. При `ready to merge` (нет прав) `verifier` коммитит отчёт со статусом и причиной, `orchestrator` назначает исполнителя merge, после фактического merge подтверждаются пост-merge проверки и отчёт актуализируется.
  - `wave-*-report.md` — после wave-проверок на ветке волны (по сценарию `architect`), коммитится в ветке волны и попадает в `main` вместе с merge ветки волны (или остаётся с `ready to merge` при отсутствии прав).
- **`implementer`** предоставляет структурированный ввод (через `.tmp` до передачи, затем в ответе/MR) и не финализирует/не коммитит канонические отчёты.
- **`scenario-tester`/`orchestrator`** предоставляют факты/ввод для wave-проверки и ретро; отчёт волны формирует `verifier`.
- **Изменения процесса не имеют обратной силы:** новые шаблоны/разделы обязательны для новых задач, волн и отчётов; существующие отчёты не приводятся задним числом к обновлённому виду.

## Сценарий проверок волны (вход для wave-report)
Сценарий описывает `architect` при декомпозиции/формировании волны: общие проверки работоспособности + проверки **добавленных или изменённых** механик. Если механики не добавлялись и не менялись, достаточно проверки факта сборки и запуска (если не указано иное).

## Правила процессного лога
- **`## Процесс (трение)`** (задача) и **`## Ретро процесса`** (волна) — только полезное для улучшения процесса/доков/шаблонов.
- Фиксировать: старт/конец или отметки раундов, роль, раунд, `T-XX`, волна, итог; неоднозначности (со ссылками на карточку/`docs/gameDocs/rules.md §…`/док/файл); лишние поиски и причину (чего не хватило в `structure.md`, ownership, шаблоне, требованиях); предложения улучшений.
- Оценка доп. затрат — **качественно** (`низко` / `средне` / `высоко`) + факты; **без метрик контекста**.
- Продуктовые/кодовые находки вне scope — в `docs/projectDocs/tech-debt.md` (`TD-*`), не в процессный лог.

```md
- **Волна / ветка волны:** …

- **Целевая ветка MR:** `wave/<N>-<slug>`
- **MR:** (ссылка/ID или причина)
- **Раунды:** 1,2,… (кратко)
- **Финализировал и закоммитил отчёт (verifier, после проверок):** …

## Выполнено (по пунктам «Что сделать»)
- …

## Изменённые/созданные файлы (только ownership)
- …

## Проверки (из «Как проверить», выполнены implementer в ветке)
- Команда → результат (или «не выполнено: причина/ограничение»)

## Верификация (verifier)
- Вердикт: verified / changes requested / blocked
- Замечания/раунды: …
- Merge в ветку волны: выполнен / `ready to merge` (причина, ссылка)
- Post-merge в контексте ветки волны (сборка+старт): команды → результат

## Процесс (трение)
- Старт/конец или отметки раундов: …
- Неоднозначности (ссылки на карточку/`docs/gameDocs/rules.md §…`/док/файл): …
- Лишние поиски и причина (чего не хватило в `structure.md`/ownership/шаблоне/требованиях): …
- Оценка доп. затрат: низко/средне/высоко (+ факты)
- Предложения по улучшению: …

## Заметки / tech-debt
- TD-* или «нет»
```

```md
## Параллелизм и ownership
- Какие T-* шли параллельно, подтверждение отсутствия пересечений `Владеет файлами`.

## Post-merge проверки по задачам (в контексте ветки волны)
- T-XX: merge/ready-to-merge; сборка (`…`) → …; старт (`…`) → …; эскалация architect при сбое: …

## Wave-проверка (по сценарию architect, на ветке волны)
- **Общие проверки работоспособности:** …
- **Добавленные/изменённые механики:** … (или «не было — проверка сборки и запуска»)
- **Сборка:** ok / fail
- **Автотесты:** ok / fail
- **Запуск / целевой сценарий:** ok / fail / n/a (по сценарию)
- **Результат:** ok / fail → при проблемах: анализ `architect`, корректирующие T-* с учётом разбивки причин по задачам волны

## Merge ветки волны в основную
- Статус: выполнен / не выполнен (`ready to merge` ветки волны + причина)
- Примечание: отчёт волны коммитится в ветке волны и попадает в основную ветку вместе с merge.

## Ретро процесса
- Агрегированные фрикции (по задачам/ролям): …
- Повторяющиеся причины: …
- Решения/улучшения на следующую волну: …

## Итоги
- Закрыто задач: …
- Открытые блокеры / новые T-* / TD-*: …
```
