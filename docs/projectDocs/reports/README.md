# Отчёты (reports)

Каталог для канонических отчётов выполнения задач/волн и file-first handoff-артефактов.

## Что хранить
- **Отчёты по задачам:** `task-T-XX-<short-slug>.md`.
- **Отчёты по волнам:** `wave-<N>-report.md`.
- **Handoff `implementer` (file-first, предпочитительно):** `docs/projectDocs/reports/handoffs/implementer-T-XX-r<N>.md` — структурированный ввод раунда в ветке задачи (команды/результаты, замечания, фрикции, ссылки). Коммитится в ветке задачи при необходимости доступа `verifier`/истории; не является каноническим отчётом.
- **Локальный черновик (опционально):** `docs/projectDocs/reports/.tmp/implementer-T-XX-r<N>.md` — gitignored scratch, не транспорт для верификации. Не требовать удаления «перед передачей», но и не использовать как единственный источник, недоступный `verifier`.

## Ownership и моменты фиксации
- **Канонический владелец отчётов — `verifier`.** Финализирует и **коммитит отчёты после прохождения проверок** (в ветке волны по процессу ветвления).
  - `task-T-XX-*.md` — после per-task проверок (при `ready to merge` — статус/причина, актуализация после фактического merge/пост-merge).
  - `wave-*-report.md` — после wave-проверок по сценарию `architect`; включает вклад `process-master` по ретро/мерам (передаётся file-first/refs, финальный коммит отчёта — `verifier`).
- **`implementer`** предоставляет handoff file-first и не финализирует/не коммитит канонические отчёты.
- **`scenario-tester`**, **`analyst`**, **`process-master`** и др. предоставляют факты/ввод через артефакты и Status Envelope (без inline-деталей в оркестрацию).
- **Изменения процесса не имеют обратной силы:** новые шаблоны/разделы обязательны для новых задач, волн и отчётов; существующие отчёты не приводятся задним числом. При анализе старых отчётов состав/форма могут отличаться — извлекать доступную информацию из любого представления и явно отмечать недостающие данные.

## Принцип передачи (анти-контекст-bloat)
- В ответах ролей/оркестратору — только **Status Envelope + refs** (пути, ветка, MR, коммит, строки/якоря при необходимости). Полные логи, диффы и копипасты запрещены.
- Подробности проверок, замечаний, причин, фрикций и мер — в handoff/отчётах/`process-improvement-log.md`/спеках.
- На доработках — **дельта** относительно предыдущего раунда/версии (что изменилось, новые результаты, refs).

## Входы для отчётов
- **Task-report:** handoff `implementer`, MR/diff refs, факты `verifier`, сценарий/DoD задачи.
- **Wave-report:** task-отчёты, сценарий проверок волны `architect`, ввод `scenario-tester` (если был), итоги merge/post-merge, вклад `process-master` (меры, эффект прошлых мер, утечки/циклы, предложения), refs на `PI-*`.

## Правила процессного лога
- **`## Процесс (трение)`** (задача) и **`## Ретро процесса`** (волна) — полезное для улучшения процесса/доков/шаблонов.
- Фиксировать: роль, раунд/этап, волна/`T-XX`, итог; неоднозначности (со ссылками на `FS-*`/карточку/`docs/gameDocs/rules.md §…`/док/файл); лишние поиски и причину; оценка доп. затрат **качественно** (`низко/средне/высоко`) без метрик контекста; предложения/принятые меры.
- Продуктовые/кодовые находки вне scope — в `docs/projectDocs/tech-debt.md` (`TD-*`), не в процессный лог.

## Шаблон: отчёт по задаче (`task-T-XX-...md`)
```md
# Отчёт задачи T-XX — <краткое имя>

- **T-XX:** …
- **Волна / ветка волны:** …
- **Ветка задачи / MR:** … (refs)
- **Раунды:** … (refs на handoff)
- **Финализировал и закоммитил отчёт (verifier, после проверок):** …

## Выполнено (по пунктам «Что сделать»)
- …

## Изменённые/созданные файлы (только ownership)
- …

## Проверки (evidence refs)
- Команды/сценарии → результат (refs на handoff/логи в артефактах; без копипаста логов)

## Верификация (verifier)
- Вердикт: verified / changes requested / blocked / ready to merge
- Замечания/раунды (дельта): …
- Merge в ветку волны: выполнен / `ready to merge` (причина, ref)
- Post-merge в контексте ветки волны: сборка/старт → результат (refs)

## Процесс (трение)
- Неоднозначности (ссылки на FS-*/карточку/rules §…/док/файл): …
- Лишние поиски и причина: …
- Оценка доп. затрат: низко/средне/высоко (+ факты)
- Предложения по улучшению: …

## Заметки / tech-debt
- TD-* или «нет»
```

## Шаблон: отчёт по волне (`wave-<N>-report.md`)
```md
# Отчёт волны Wave N — <название>

- **Дата:** …
- **Ветка волны / target:** … (refs)
- **Сценарий проверок волны (architect):** ref/кратко — общие + добавленные/изменённые механики (или «только сборка и запуск»)
- **Финализировал и закоммитил (verifier, после проверок):** …

## Задачи волны
| T-* | Статус | Ветка/MR (refs) | Вердикт | Отчёт задачи | Примечание |
|-----|--------|------------------|---------|--------------|------------|

## Параллелизм и ownership
- Группы/подтверждение отсутствия пересечений (ref на launch-план).

## Post-merge проверки по задачам (в контексте ветки волны)
- T-XX: merge/ready-to-merge; сборка/старт → результат; эскалации (refs)

## Wave-проверка (по сценарию architect, на ветке волны)
- **Общие проверки работоспособности:** …
- **Добавленные/изменённые механики:** … (или «не было — сборка и запуск»)
- **Сборка / автотесты / запуск/сценарий:** ok|fail|n/a (refs)
- **Результат:** ok|fail → при проблемах: triage `architect`, маппинг «причина/затронутые T-* → корректирующая T-*»

## Merge ветки волны в основную
- Статус: выполнен / не выполнен (`ready to merge`, причина, ref)

## Ретро процесса (вклад process-master / факты участников)
- Проблемы и фрикции (с refs): …
- Принятые/предложенные меры и влияние на сложность: …
- Эффект мер прошлых волн (помогло/не помогло/утекло, пробелы данных): …
- Циклы/регрессии (если есть): …
- Ссылки на `PI-*` в `docs/projectDocs/process-improvement-log.md`: …

## Итоги
- Закрыто задач: …
- Открытые блокеры / новые T-* / TD-* / PI-* : …
```
